# mcp-sluice 設計

mcp-sluice は、複数の子 MCP サーバーを 1 つのエンドポイントに束ねる MCP サーバー。次の機能を持つ。

- 認証: authentik (OIDC) で利用者を認証する。
- 権限: 利用者のグループとツールごとに allow/ask/deny を掛ける。
- Code Mode: TypeScript でツールを呼ぶスクリプトを実行する。
- 観測: OpenTelemetry で trace・metrics・log を送る。

この文書の読者は、mcp-sluice を実装・変更する人。この文書が仕様の正本になる。

外部依存の事実の書き方:

- 一次情報で確かめたもの: 根拠に書き、各出典に確認した日を添える。外部の契約が今も成り立つかを、後でその日から判定するため。
- 確かめられなかったもの: 「未確認」と書き、選定の根拠にしない。

一次情報は次のもの:

- 仕様の repo
- ソース
- 公式 docs

「将来」と書いた節は、最初の公開に含めない。最初の版のデータの持ち方が、それを後から足せる形になるように書いてある。

## 0. 前提

- 公開リポ (OSS) として作る。
  - 認証は OIDC の一般の仕組みで書く。設定例と手順は authentik で示す。
- 利用者は複数人。
  - authentik の application の policy を通った人が、利用者になれる。
  - 利用者ごとの権限は、トークンの `groups` で分ける。
- 対象のクライアント:
  - Claude Code
  - claude.ai (Claude Desktop と mobile を含む)
  - Codex
  - ChatGPT

  claude.ai に含まれるものは、どれも同じ callback の URL で接続する (`claude.com/docs/connectors/building/authentication` の Callback URLs、2026-10-28)。
- 守るもの:
  - エージェントの誤り。プロンプトインジェクションで書かれたスクリプトが外部へ持ち出すことも含む。
  - 誤った相手への送信。利用者 A の資格情報や承認が、利用者 B の要求に使われることも含む。
  - 平文でホストの外へ出すこと。
  - トークンの残存と流用。
- 信頼するもの:
  - ゲートウェイが動くホスト
  - 管理者が登録した子サーバー
  - authentik
  - 観測の基盤

## 1. 全体の構成

```
 MCP クライアント (Claude Code / claude.ai / Codex / ChatGPT)      ブラウザ (承認のページ)
        │ Streamable HTTP + Bearer (authentik の JWT)                    │ OIDC ログイン (同じ authentik)
        ▼                                                                  ▼
 ┌──────────────────────────── mcp-sluice (1 プロセス, Deno) ─────────────────────────────┐
 │ HTTP 層    : /mcp, /.well-known/oauth-protected-resource, /i/<id> (利用者の操作のページ) │
 │ 認証       : JWT 検証 (JWKS)、ブラウザのセッション                                     │
 │ カタログ   : 子のツールを名前空間つきで合成し、利用者ごとに policy で絞る               │
 │ Policy     : allow / ask / deny (グループつきの規則)                                    │
 │ 利用者の操作: 承認を elicitation か URL で利用者に求め、中断した要求を再開する           │
 │ Code Mode  : 型検査と変換 (typescript) → QuickJS-WASM (worker で実行)                   │
 │ 子の管理   : 子への接続、list_changed の受信                                            │
 │ 観測       : OpenTelemetry (trace / metrics / log) を OTLP で送る                         │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
        │ stdio (共有の子プロセス) / Streamable HTTP (共有の資格情報)
        ▼
 子 MCP サーバー群

 観測 (compose に同梱): Tempo (trace) / Loki (log) / Prometheus (metrics) / Grafana (UI, authentik でログイン)
```

- 実行時:
  - Deno 2.x を使う。
  - 公式 TypeScript SDK v2 (`@modelcontextprotocol/server` 2.4.0) を使う。README は、次で動くと書く (https://github.com/modelcontextprotocol/typescript-sdk の README、2026-10-28):
    - Node.js
    - Bun
    - Deno
- 持つ状態:
  - メモリだけに持つ: 中断した要求 (承認待ちの Code Mode の実行など)。
  - メモリの状態があるので、レプリカは 1 つにする。
  - 将来の `per_user` (3.3 節) で、利用者ごとの子のトークンを SQLite のファイルに暗号化して持つ。
- 配る形: コンテナイメージ。docker compose の例も付ける (ゲートウェイと観測の基盤)。

## 2. プロトコルの版

- 2 つの世代を両方受ける。
  - 2026-07-28 (最新):
    - `initialize` もセッションも無い。
    - サーバーからクライアントへの要求は、`tools/call` の結果として `input_required` を返し、クライアントが再送する形 (Multi Round-Trip Requests。以下 MRTR) だけになった。
  - 2025-11-25 まで:
    - `initialize` とセッションがある。
    - POST の SSE の流れの中で `elicitation/create` を送れる。
- 両方を受ける理由:
  - claude.ai の connector の docs が挙げる authorization の仕様は 2025-11-25 まで (https://claude.com/docs/connectors/building/index.md の Specification version、2026-10-28)。
  - Claude Code は 2026-07-28 に対応している (https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md の 2.1.281 に、2026-07-28 の接続での URL mode の elicitation がある。2026-10-28)。
- SDK v2 は 1 つの handler で両世代を受けられる (https://github.com/modelcontextprotocol/typescript-sdk の `docs/protocol-versions.md` と `examples/dual-era/README.md`、2026-10-28)。
- 2025-11-25 の経路を外せる条件: 対象のクライアント (0 節) が、どれも 2026-07-28 で接続するようになったとき。
  - 確かめ方: 11 節の実測 3。
  - 追跡先: anthropics/claude-ai-mcp#153 (claude.ai の elicitation の対応の要望)。
- 子へは、SDK v2 の client を `versionNegotiation: { mode: 'auto' }` で使う。
- `tools/list` の結果:
  - 利用者ごとに絞るので、`cacheScope: "private"` を付ける (2026-07-28 の caching)。
  - `ttlMs` は短めにし、`list_changed` を併用する。
    - `ttlMs` は、仕様が勧める古さの上限。仕様は、クライアントが結果を受けてから `ttlMs` の間、結果を新しいとみなすよう勧める。0 なら、すぐに古いとみなし、クライアントは要るたびに取り直してよい (https://github.com/modelcontextprotocol/modelcontextprotocol の `schema/2026-07-28/schema.ts` の `CacheableResult`、2026-10-28)。クライアントがこれを守るか (`ttlMs` の後に `tools/list` を取り直すか) は未測定 (11 節の実測 3)。
    - 2025 系の結果には `ttlMs` が無く、一覧を取り直す時期はクライアントが決める。
    - クライアントへ `list_changed` を出す時と送る相手は、4.3 節の「クライアントへの `list_changed`」。クライアントがそれに応じて一覧を取り直すかは未測定 (11 節の実測 3)。
    - 一覧を決めるものの変化ごとに、一覧へ届く経路:

      | 変化 | 2026 系の `ttlMs` | `list_changed` | 2025 系 |
      | --- | --- | --- | --- |
      | 利用者の groups が変わった | `ttlMs` の後の `tools/list` で届く | 出さない (下の比較) | クライアントが一覧を取り直すまで届かない。呼び出しの判定 (5.2 節) では効く |
      | 設定が変わった (再起動で反映する。4.1 節) | `ttlMs` の後の `tools/list` で届く | 出さない | クライアントが一覧を取り直すまで届かない |
      | 子との接続が切れた | `ttlMs` の後の `tools/list` で届く | 出す | `list_changed` で届く |
      | 定義を取り直せなくなった | `ttlMs` の後の `tools/list` で届く | 出す | `list_changed` で届く |
      | 子が `list_changed` を送った | `ttlMs` の後の `tools/list` で届く | 出す | `list_changed` で届く |
      | 取り直せなかった定義が取り直せた | 下の手順で届く | 取り直しが成功した時に出す | 下の手順で届く |
      | 子が `list_changed` を送らずに定義を変えた | 下の手順で届く。上限は寿命 (4.3 節) と `ttlMs` の和 | 取り直しが成功した時に出す | 下の手順で届く |

      - groups の変化は、どの経路でも、変化の後に発行されたトークンの要求から効く。遅れは access token の寿命 (6.3 節の「groups の変化が効く時期」。未確認)。
      - 取り直しを経て届く変化 (表の下の 2 行) は、次の順に進む:
        1. 取り直す時期 (4.3 節) の後に、その定義を使う最初の要求で定義を取り直す。取り直しは要求で起きる:
           - 2026 系: `ttlMs` が過ぎた後の `tools/list` が、その要求になりうる。
           - 2025 系: クライアントが次に一覧か、その定義を使う呼び出しを送るまで、取り直されない。
        2. 取り直しが成功すれば、クライアントへ `list_changed` を出す。
    - (将来) `per_user` の子のトークンの失効・差し替えと、利用者が子の接続を切ったこと (3.3 節の「定義を捨てるとき」) は、2026 系の `ttlMs` で一覧に届く。
    - 他のものの変化を一覧に出す方式の比較:
      - `ttlMs` を 0 にする: 古さは無くなるが、`tools/list` の回数が、クライアントが一覧を使う回数に比例する。採らない。
      - groups の変化で `list_changed` を出す: ゲートウェイが groups の変化を知るのは、次の要求のトークンを受けたときだけ (6.3 節の「groups の変化が効く時期」) で、変化の時点に出せない。採らない。
      - 短めの `ttlMs` (採る): 古さの上限は `ttlMs` で、`tools/list` の回数は `ttlMs` あたり多くて 1 回。
    - どちらでも、古い一覧で権限は広がらない (5.2 節の、呼び出しのたびの判定)。

## 3. 認証

### 3.1 authentik でできること・できないこと

authentik 2026.8.5 と main のソースで確認した (https://github.com/goauthentik/authentik の `authentik/providers/oauth2/` と `blueprints/system/providers-oauth2.yaml`、2026-10-28)。

機能の有無:

| 機能 | 状態 | 影響 |
| --- | --- | --- |
| Dynamic Client Registration (DCR) | 有り。ただし `goauthentik.io/oidc/dcr` scope を持つ Bearer が要る | 匿名で登録しにくる MCP クライアントは 401 で失敗する |
| Client ID Metadata Documents (CIMD) | 無し | 使えない |
| RFC 8707 `resource` | 読まない | `aud` をゲートウェイに向けられない |
| RFC 8414 のメタデータ | 有り。`/.well-known/oauth-authorization-server/application/o/<slug>/` (`urls_root.py`) が、OIDC discovery (`/application/o/<slug>/.well-known/openid-configuration`) と同じ view で返す | クライアントが作る RFC 8414 の URL が末尾の `/` まで一致して届くか、届かなければ OIDC discovery に落ちるかは未確認 (11 節の実測 1) |
| refresh token | `offline_access` のときだけ出る。既定で rotation する | claude.ai の要件 (公開クライアントの rotation) を満たす |
| 非対称の署名と JWKS | 署名鍵を設定すれば有り | 非対称の署名鍵を必ず設定する |

トークンと登録の値:

| 項目 | 既定・値 | このゲートウェイの扱い |
| --- | --- | --- |
| `aud` | provider の client_id | client_id で検証する |
| `sub` | 既定は `hashed_user_id` (authentik の設置ごとに違う) | 利用者の鍵は (`iss`, `sub`) にする |
| redirect URI | strict か regex (`fullmatch`) | loopback の任意のポートを regex で通す |
| `groups` | 既定の `profile` の scope mapping に入る。access token にも入る (`include_claims_in_id_token` の既定は true) | policy にそのまま使う |

### 3.2 方式: 事前登録した公開クライアント 1 つ

- authentik に作るもの:
  - application と OAuth2 provider を 1 組作る。
  - client type は public、署名鍵は非対称にする。
  - redirect URI (regex) を登録する。

    | クライアント | redirect URI |
    | --- | --- |
    | claude.ai | `https://claude\.ai/api/mcp/auth_callback` |
    | Claude Code | `http://(localhost\|127\.0\.0\.1):\d+/callback` |
    | Codex | 上と同じ形で、末尾に `/<id>` が付くことがある (未確認。実測で決める) |
    | mcp-sluice 自身 (ブラウザのページ) | `https://<公開ホスト>/auth/callback` |

  - scope: `openid profile email offline_access`
  - 誰が使えるかは、application に結ぶ policy で決める。
- ゲートウェイの役割 (resource server):
  - `/.well-known/oauth-protected-resource` (RFC 9728) を出す。
    - `resource` = 公開 URL
    - `authorization_servers` = [issuer]
  - 未認証には 401 と `WWW-Authenticate: Bearer resource_metadata="…"` を返す。claude.ai は 401 でしか認証を始めない (`claude.com/docs/connectors/building/authentication` の Serve discovery metadata。200 に付けた `WWW-Authenticate` は無視されると書いてある。2026-10-28)。
  - JWT は次を検証する (署名と期限の検証は、下の JOSE のライブラリに任せる):
    - JWKS での署名
    - `iss`
    - `exp`・`nbf`
    - `aud` == 設定の client_id
- ブラウザのページ (`/i/<id>`):
  - provider は 1 つ。同じ client で authorization code + PKCE のログインをし、セッションの cookie を発行する。
- cookie は、上の JWT と同じく JOSE のライブラリに任せ、JWS (対称鍵。HS256) で署名する。鍵の渡し方は 9 節。
  - cookie は期限 (`exp`) を持つ。値は 4.4 節の「ブラウザのセッション」の寿命。
- JOSE のライブラリ:
  - 候補は `npm:jose`。
  - 次は未確認。実装の時に一次情報で確かめて canon に足し、採る版を `deno.json` に入れる:
    - Deno で動くか。
    - 検証の API が、既定で `exp` を検査するか。
- 設定は 2 つの値だけにする: `issuer` と `client_id`。
- authentik 以外の IdP でも同じ形で動くと見込む。未確認。その IdP で次を確かめる (authentik で確かめた内容は 3.1 節の表):
  - クライアントがメタデータ (RFC 8414 か OIDC discovery) に届く。
  - access token が JWT で、JWKS で署名を検証できる (上の JWT の検証)。
  - access token の `aud` が client_id になる。
  - loopback の任意のポートの redirect URI を登録できる。
  - access token に `groups` の claim が入る。
- 退けた方式: ゲートウェイ自身を OAuth の AS にし、ログインだけ IdP に任せる。
  - 退けた理由: トークンの発行・保存・失効を自前で抱えることになる。対象のクライアントは、どれも事前登録の client_id を受ける。
  - ただし、クライアントが authentik のメタデータ (RFC 8414 か OIDC discovery。3.1 節) に届かなければ、この方式が要る。メタデータを代わりに出すだけでは済まない (クライアントは `issuer` と discovery の URL の一致を検査する)。実測で決める。

### 3.3 子サーバーへの資格情報

- 受け取ったトークンを子へ流さない。MCP の仕様は token passthrough を禁止している。
- 子の資格情報は、管理者が env の名前で渡す固定のものだけ。全利用者で共有する (以下 `shared`)。種類 (設定の項目は 4.1 節):
  - Bearer (`bearer_env`)
  - ヘッダ (`headers_env`)
  - stdio の子の環境変数 (`env_from_parent`)
  - 認証なし (`auth: none`)
- `shared` の子は誰の要求でも同じ身元で動く。誰がその子を使えるかは、policy のグループで絞る。
- 資格情報の持ち方を選ぶ設定は、将来の `per_user` を足すときに設定へ加える。

#### 将来: `per_user`

利用者ごとに、ゲートウェイが子の OAuth の client になってトークンを得る。HTTP の子だけで使える。

- 手順: 仕様の URL mode elicitation の節が定める形に従う。
  1. 利用者がまだ接続していない子のツールを呼んだら、「接続」の操作 (6 節) を作る。
  2. ページ (`/i/<id>`) で、ログインのセッションの (`iss`, `sub`) が要求の (`iss`, `sub`) と一致することを確かめる。一致すれば、子の AS へ送る。仕様は、URL を開いた人の確認を求めている。
  3. 戻ってきたトークンを、次のように保存する:
     - (`iss`, `sub`, server id) に結ぶ。
     - 保存のたびに、新しいトークンの id (128 bit の乱数。作り方は 4.4 節) を振る。
     - 暗号化して保存する。
- 子の AS へのクライアント登録は、次の順で試す。CIMD を使う場合、ゲートウェイは自分のメタデータの文書を公開する。
  1. 事前登録
  2. CIMD
  3. DCR
- 暗号化の鍵は env で渡す。鍵を失ったら、保存したトークンは全部無効になり、利用者は再接続する。
- 子が返すツールの定義は、利用者によって違いうる。鍵は、4.4 節の表の「単位ごとの記録」の行に従う。
- 定義は、利用者が子に接続したときに取る。
- 定義の古さ・寿命・取り直せなかったときの扱いは、4.3 節に従う。
- 古い定義と取り直せなかった定義の取り直し:
  - 取り直す時期は 4.3 節。
  - `per_user` の子の取得には、同時に取る数の上限を置く。7.2 節の同時に動く実行の上限と同じ物差しで比べ、同じ結論になる:
    - 利用者ごとと全体の 2 つの上限を置く。
    - どちらも固定値。値は実装で計測して決める。
    - 利用者ごとの上限は、全体の上限より小さくする。
  - `shared` の子の取得は、この上限に数えない。単位ごとに同時に 1 つまで (4.3 節) で、`shared` の子の数は設定 (4.1 節) で有限に決まる。
  - 上限の扱い:
    - 上限の検査を受けるのは、進行中の取得の表 (4.3 節) に単位を新しく足す取得だけ。世代番号の食い違いの後の 2 回目の送信は、同じ取得の中で行う。
    - 1 つの要求が取り直しを始めるときは、表にまだ無い `per_user` の子の単位を、単位の鍵 (子のトークンの id) の辞書順に並べ、先頭から 1 つずつ次を行う:
      1. 利用者ごとと全体の数を、表から数える (下の「上限の数え方」)。
      2. どちらも上限より少なければ、その単位を表に登録する。どちらかが上限に達していれば、その単位と後の単位を登録しない。

      表にまだ無いかの確認から最後の登録までを、間に await を挟まずに行う。挟むと、同時に来た要求が同じ数を見て、上限を超えて登録する。
    - 登録しなかった単位の定義は、取り直せなかった定義 (4.3 節) として扱う。`tools/call` の理由の決め方は 4.3 節。
    - 上限の数え方 (6.3 節と 7.2 節の上限も、これに従う): 数は、対象の集合の大きさとして数える。利用者ごとの数は、集合の要素のうち、その利用者のものの数。別の計数器を持たない。
    - 取り直しの上限が数える集合と、要素の利用者の決め方は、4.3 節の進行中の取得の表。
  - 取得の終わり方ごとの扱いと、表から外す手順は 4.3 節。
- 定義が有効かは、使うときに 4.3 節の「記録の有効」で判定する。子との接続の切断と、定義の最長の寿命は、この判定で定義を無効にする。
- 定義を捨てるとき: 次のどれかで、その id の記録 (定義か失敗の後の間隔。4.3 節) と世代番号を、まとめて捨てる:
  - 子のトークンが失効した。
  - 子のトークンが差し替わった (トークンの id が変わる)。
  - 利用者が子の接続を切った (`per_user` のトークンを消した)。
- 世代番号を採った記録。案を次の物差しで比べた:
  - 状態の数
  - 子の `list_changed` への依存
  - 取り直しの回数と経路

  | 案 | 状態の数 | 子の `list_changed` への依存 | 取り直しの回数と経路 | 採否 |
  | --- | --- | --- | --- | --- |
  | 定義ごとの印 | 定義ごとに 1 つ。`list_changed` のたびに、その接続のトークンの id の定義に印を書く | 依存する | 古い定義を使う要求のたびに、その利用者の分を 1 回。要求の経路で取り直す | 採らない。取得の最中に届いた `list_changed` の印が、その取得で得た定義に付かない |
  | `list_changed` の時点で全利用者分を取り直す | 足さない | 依存する | `list_changed` のたびに、接続している利用者の数だけ。通知の経路で、使われない定義も取り直す | 採らない |
  | 世代番号 | 子のトークンの id ごとに 1 つと、定義ごとに 1 つ。`list_changed` と接続の切断で書くのは、そのトークンの id の 1 つだけ | 依存する | 古い定義を使う要求のたびに、その利用者の分を 1 回。要求の経路で取り直す | 採る |

- 利用者に見せる一覧は、`tools/list` のたびに、その利用者の定義と接続の状態から作る。まだ接続していない利用者の一覧には、`gateway__connect` を載せる。

## 4. 子サーバーの登録と名前

### 4.1 設定ファイル

1 つの宣言的なファイル (YAML) にする。JSON Schema で検証し、変えたら再起動で反映する。

子へ渡す値は、どれも親の環境変数の名前で書く (9 節)。名前の形は `^[A-Za-z_][A-Za-z0-9_]*$`。子へ渡す値:

- `bearer_env`
- `headers_env` の各値
- `env_from_parent` の各値

```yaml
auth:
  issuer: https://auth.example.com/application/o/mcp-sluice/
  client_id: mcp-sluice
default: ask                        # どの規則にも当たらないとき
servers:
  github:
    transport: { type: http, url: https://api.githubcopilot.com/mcp/ }
    auth: { bearer_env: GATEWAY_GITHUB_TOKEN }   # 値は親の環境変数の名前
    groups: [dev]                   # この子を使える人 (5.1 節)
    rules:                          # 評価の順は 5.1 節
      - { tools: "delete_*", groups: [admins], decision: ask }
      - { tools: "delete_*", groups: ["*"], decision: deny }
      - { tools: ["get_*", "list_*", "search_*"], groups: ["*"], decision: allow }
  docs:
    transport: { type: http, url: https://mcp.example.com/ }
    auth: { headers_env: { X-Api-Key: GATEWAY_DOCS_API_KEY } }   # キーはヘッダ名。値は親の環境変数の名前
    groups: ["*"]
    rules:
      - { tools: "*", groups: ["*"], decision: allow }
  fs:
    transport: { type: stdio, command: /usr/local/bin/fs-mcp, args: [--root, /data] }
    env_from_parent: { FS_TOKEN: GATEWAY_FS_TOKEN }   # キーは子の変数名。値は親の環境変数の名前
    groups: [dev]
    rules:
      - { tools: "write_*", groups: ["*"], decision: ask }
      - { tools: "*", groups: ["*"], decision: allow }
gateway:                            # ゲートウェイ自身のツールにも同じ規則を掛ける
  rules:
    - { tools: "*", groups: ["*"], decision: allow }
```

- 起動時の設定の検査で、次のどれかに当たれば起動を失敗させる:
  - どこかの階層に、JSON Schema に無いキーがある (`additionalProperties: false`)。綴りを誤ったキーが、黙って無視されないため。
  - 空の配列がある (`minItems: 1`)。対象:
    - server の `groups`
    - rule の `groups`
    - rule の `tools`
  - server か rule に `groups` が無い。全員に当てるなら、`groups` に `"*"` を書く (5.1 節)。
  - server id が 4.2 節の形に外れる。
  - rule の `tools` の文字列が 5.1 節の形に外れる。
  - rule の `tools` の文字列が、その server の公開名の接頭辞 `<server id>__` で始まる (5.1 節)。
  - `auth.issuer` か HTTP の子の `url` が `https:` でない。ただし、loopback の `http:` は両方に許す。平文でホストの外へ出さないため (0 節)。
    - loopback の判定: URL を parse した `hostname` が、次のどれかと等しい。文字列の前方一致で比べると、`http://localhost.example.com/` のような外のホストを通す。
      - `127.0.0.1`
      - `[::1]`
      - `localhost`
    - issuer に loopback の `http:` を許す理由: 次の 3 つを 1 つのホストに置く形 (開発や、1 人で使う配備) のため。
      - ゲートウェイ
      - authentik
      - クライアント (Claude Code など)

      issuer は、ゲートウェイが JWKS を取る先で、クライアントが認可に使う先でもある (3.2 節の `authorization_servers`)。loopback なら、どちらの通信もホストの外へ出ない。
    - 比べた案: loopback でも `https:` を要る。採らない。通信がホストの外へ出ないので、守るもの (0 節の「平文でホストの外へ出すこと」) に当たらず、開発と 1 人の配備に証明書の発行と信頼の設定を求めるだけになる。
  - 子へ渡す値の環境変数の名前が、上の形に外れる。この検査は、`Deno.env.get` を呼ぶ前に止める。`Deno.env.get` は、空・`=` を含む・NUL を含む名前で `TypeError` を投げ、他の名前 (非 ASCII など) は検査しない (canon: facts/deno/env-get-key-validation)。
  - 子へ渡す値の環境変数を `Deno.env.get` で読むと、投げる (どの種類でも)。値が UTF-8 として不正なときの `InvalidData` と、`--allow-env` を名前で絞ったときの `NotCapable` を含む (同じ canon)。
  - 子へ渡す値が指す環境変数が、次のどれかに当たる。ここの HTTP whitespace は tab・空白・CR・LF の 4 字で、前後から落とすのはこの 4 字だけ (`String.prototype.trim` は U+00A0 なども落とすので使わない):
    - 無いか空。HTTP の子の値 (`bearer_env`・`headers_env`) では、前後の HTTP whitespace を落とすと空になる値も空とする。判定は環境変数の値で行い、`Bearer ` を付けた後では行わない。
    - HTTP の子の値が、ヘッダの値として `Headers` に入らない。入れ方は、`append` してから `get` で読み戻す。`bearer_env` は、`Authorization` の値 `Bearer <値>` として入れる。次のどちらかなら当たる:
      - `append` が `TypeError` を投げる。次の値は、これで止まる:
        - 途中に CR か LF を含む値 (前後に HTTP whitespace もあるものは、下の読み戻しで止まる)
        - 位置によらず NUL を含む値
        - U+00FF を超える文字を含む値
      - 読み戻した値が、入れた値から前後の HTTP whitespace を落としたものと違う。
        - この判定が止める値: deno 2.9.8 の `Headers` が、投げずに空文字として受ける値。前後に HTTP whitespace があり、途中に CR か LF がある (例: ` a\nb`)。
        - 外す条件: deno の版を上げるたびに、canon の実測 (下の出典の `Headers`) を測り直す。` a\nb` が `append` で `TypeError` になれば、この判定とそのテストを外す。上流 (deno) への報告は未。

      前後の HTTP whitespace は、`Headers` の落とし方に任せて、値をそのまま受ける。
  - server の項目が、transport の `type` に合わない。JSON Schema で `type` ごとに書ける項目を分ける:
    - `auth`: `http` の子だけ。
    - `env_from_parent`: `stdio` の子だけ。
  - `http` の子の `auth` が、次のちょうど 1 つでない (`auth` を省いたときを含む)。子 1 つに、認証の形は 1 つ。JSON Schema の `oneOf` で閉じる:
    - `{ bearer_env: … }`
    - `{ headers_env: … }`
    - `none` (認証なしで接続する。3.3 節)

    `auth` を省いたときも起動を失敗させるのは、`auth` 行の消し忘れで、資格情報で守るつもりの子へ認証なしの接続が通るのを防ぐため。
  - `headers_env` のキーを、1 つの `Headers` へ順に `append` するとき、次のどれかに当たる:
    - `append` が `TypeError` を投げる (HTTP の field name の形に外れる)。
    - `append` の前に、`has` が真になる。`Headers` は名前の大文字小文字を区別しない。RFC 9110 も field name の大文字小文字を区別しない (5.1 節)。
    - 大文字小文字を無視して、ゲートウェイか SDK が自分で決めるヘッダの名前と等しい。名前の一覧 (これで全部):
      - `Authorization`: `bearer_env` で渡す。
      - HTTP の message の枠を決める名前:
        - `Host`
        - `Content-Length`
        - `Transfer-Encoding`
        - `Connection`
      - MCP の Streamable HTTP が使う名前 (仕様と SDK が使う名前は、下の出典):
        - `Accept`
        - `Content-Type`
        - `Last-Event-ID`
        - `Mcp-` で始まる名前 (前方一致)
  - `env_from_parent` のキーが `^[A-Za-z_][A-Za-z0-9_]*$` に外れる。広げるのは、要る子が出たとき。
  - cookie の署名の鍵 (9 節) の環境変数 `MCP_SLUICE_COOKIE_KEY` が、次のどれかに当たる:
    - `Deno.env.get` で読むと投げる (上の子へ渡す値と同じ)。
    - 無いか空。
    - base64 で読めない。判定は、値を @std/encoding の `decodeBase64` で読み、読んだバイト列を `encodeBase64` で符号化し直して、値と一致するかで行う。投げるか一致しなければ、読めないものとする。`decodeBase64` は padding の省略・余分な `=`・余りの bit が 0 でない形 (例: `QR==`) も受けるので、読めたことだけでは判定にならない。`encodeBase64` の字母は `A-Za-z0-9+/` で、padding は `=` (canon: facts/deno/std-encoding-base64。@std/encoding 1.0.11)。そのため、空白・改行・URL-safe の字母を含む値も読めないものになる。
    - 読んで 32 バイトに足りない。
- 子へ渡す値の検査 (上) の失敗の文言は、server id と項目 (`headers_env` ならキー) だけで作る。他のものは、秘密を含みうる:
  - 値。
  - Deno が投げたものの文言:
    - `Headers` の `TypeError`: 名前と値をそのまま含む (canon: facts/deno/headers-validation)。
    - `Deno.env.get` の `TypeError` と `NotCapable`: 名前を含む。`InvalidData`: 値を含む (canon: facts/deno/env-get-key-validation)。
  - 環境変数の名前。名前の欄に秘密を誤って書いたとき、文言からログへ漏れる (0 節の利用者の誤り)。
- cookie の署名の鍵の検査 (上) の失敗の文言は、`MCP_SLUICE_COOKIE_KEY` の名前 (固定で、秘密でない) と、当たった項目だけで作る。値と Deno が投げたものの文言は、鍵を含みうる。
- `Headers` に入るかの検査の機構の比較。物差し:
  - 依存する契約
  - 規則の数
  - 漏れの経路 (検査を通った値が、送る時に変わるか投げる)

  | 案 | 依存する契約 | 規則の数 | 漏れの経路 | 採否 |
  | --- | --- | --- | --- | --- |
  | `Headers` に入れて読み戻す | deno の `Headers`。2.9.8 は仕様から外れる (下の出典の `Headers`) ので、読み戻しの比較を足す | 値は 2 つ (`TypeError` と読み戻しの比較)、名前は 2 つ (`TypeError` と `has`) | 送る時に値を入れるのと同じ `Headers` で判定する。版を上げて受け方が変わっても、判定と送る時が一緒に変わる | 採る。判定と送る時の受け方が、同じ実装で揃う。読み戻しの比較は、deno 2.9.8 の逸脱 (上の「この判定が止める値」) の分だけ要る |
  | 字句の規則を書く (WHATWG Fetch の、`Headers` が名前と値に掛ける規則) | WHATWG Fetch の規則。deno の版に依らない。RFC 9110 の `field-name`・`field-value` の集合とは違う (RFC の値は、tab を除く C0 制御文字と DEL も含めない) | 5 つ (名前の `token`、値の NUL、CR か LF、U+00FF を超える文字、前後の HTTP whitespace) | canon の実測 (deno 2.9.8) の範囲では無い。規則を満たす値は、送る時に変わらない。上の「この判定が止める値」は、CR か LF の規則が止める | 採らない。送る時の `Headers` と別の規則 (5 つ) を管理する |

- stdio の子の環境は、次の 2 つを合わせたもの。同じ名前なら、`env_from_parent` の値を使う。重ねることは、SDK の実装で確かめた契約 (7.2 節の「型定義に書かれておらず、実装で確かめたもの」):
  - SDK の `getDefaultEnvironment()` が返す変数 (canon: facts/mcp-typescript-sdk/stdio-default-env)
  - `env_from_parent` に書いた変数
- stdio の子の環境の決め方の比較。物差し:
  - 子へ渡る親の変数
  - 要る手当て
  - SDK の stdio transport を使えるか

  | 案 | 子へ渡る親の変数 | 要る手当て | SDK の stdio transport | 採否 |
  | --- | --- | --- | --- | --- |
  | SDK の既定に重ねる | `getDefaultEnvironment()` の変数と、`env_from_parent` | 無し | 使える | 採る。既定の変数は、0 節で信頼するホストの環境の値 |
  | `env_from_parent` だけにする | `env_from_parent` だけ | 子を SDK の外で起こす | 使えない (既定に重ねる形を外せない。canon は上と同じ) | 採らない。SDK の stdio transport を捨てる |
  | 既定の変数を空の値で上書きする | 既定の変数が、空の値で残る | 既定の変数を全部 `env_from_parent` に書く | 使える | 採らない。既定の変数を子の環境から消せない |

- 出典 (2026-10-28 に確認):
  - RFC 9110: https://github.com/httpwg/httpwg.github.io の `specs/rfc9110.xml` (HTTP WG が公開する RFC の原稿)。
  - `Headers` (WHATWG Fetch の仕様と、deno 2.9.8 の実測): canon: facts/deno/headers-validation。
  - MCP の Streamable HTTP のヘッダ: https://github.com/modelcontextprotocol/modelcontextprotocol の `docs/specification/2025-11-25/basic/transports.mdx` と `docs/specification/2026-07-28/basic/transports/streamable-http.mdx`。
  - SDK が自分で決めるヘッダの名前と、stdio の子の既定の環境: npm の `@modelcontextprotocol/client` 2.4.0 の tarball の `dist` (ヘッダは `index.mjs` の `_commonHeaders`・`_applyBodyDerivedHeaders`、環境は stdio transport の `getDefaultEnvironment`)。
    - SDK の版を上げるたびに、ヘッダの名前の一覧と既定の環境を確かめ直す。
    - 外せる条件: SDK の型定義か docs がヘッダの名前を書いたら、そちらを出典にする。
- 未確認: `encodeBase64` の形 (canon: facts/deno/std-encoding-base64) が、RFC 4648 の 4 節 (標準の base64) に当たるか (一次情報: https://www.rfc-editor.org/rfc/rfc4648)。

### 4.2 名前

- 公開する名前は `<server>__<tool>`。
  - 区切りは `__` にする。Messages API のツール名は `^[a-zA-Z0-9_-]{1,128}$` で、`.` を含められない (`platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools`、2026-10-26)。
- server id は `^(?=.{1,16}$)[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`。
  - 公開名の区切りは最初の `__` に決まる。
  - JS の識別子として使える。
  - `gateway` は予約する。
- 合成した名前が `^[A-Za-z0-9_-]{1,64}$` に収まらないツールは公開しない。そのときは警告を log に出す。
  - 64 の根拠: OpenAI の function 名の上限。OpenAI の API の OpenAPI 定義は、Chat Completions の `FunctionObject` の `name` を「a maximum length of 64」と書く (https://github.com/openai/openai-openapi の `openapi.yaml`、2026-10-28)。Responses の `FunctionTool` の `name` には上限の記載が無い。
  - Claude Code (v2.1.292 以降) は名前の前に `mcp__<登録名>__` を足し、128 文字を超えたツールを落とす (`code.claude.com/docs/en/mcp` の「Tools with names longer than 128 characters」と、https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md の 2.1.292。2026-10-28)。
- Code Mode からは `tools.<server>.<tool>(args)` で呼ぶ。名前に `-` や `.` があれば `tools.github["create-issue"]` の形にする。

### 4.3 子の管理

この節の状態 (世代番号の単位・世代番号・単位ごとの記録・進行中の取得) の鍵・等しさ・寿命は、4.4 節の表。

- 起動時に接続する。切れたら、指数バックオフで再接続する (SDK v2 の client が再接続を持てば、それを使う)。
- ツールの定義 (`shared` の子の一覧と、3.3 節の `per_user` の子の定義) は、世代番号の単位ごとの記録に持つ。
  - 世代番号の単位:
    - `shared` の子: server id
    - `per_user` の子: 子のトークンの id。1 人の利用者の接続・切断・`list_changed` は、他の利用者の定義を古くしない。
  - 記録は単位ごとに 1 つで、次のどちらかを持つ:
    - 定義
    - 失敗の後の間隔 (下)

    どちらも、次の 2 つを持つ:
    - 世代番号: 取得 (下) が最後に `tools/list` を送る前に読んだもの。
    - 時刻: 取得が最後に `tools/list` を送った時刻。定義の寿命と間隔の起点。
  - 記録を置くのは、取得の終わり (下の finally の 0) だけ。置くと、前の記録は置き換わる。記録を捨てるのは、3.3 節の「定義を捨てるとき」(`per_user` の子) だけ。
  - 記録の有効: 記録は書き換えず、使うときに判定する。有効な記録だけを使う:

    | 記録 | 有効の条件 |
    | --- | --- |
    | 定義 | 記録の世代番号 = 今の世代番号で、記録の時刻から定義の最長の寿命 (下) が過ぎていない |
    | 失敗の後の間隔 | 記録の世代番号 = 今の世代番号。間隔が過ぎた後も、次の失敗で間隔を延ばす起点として有効 (下の「失敗の後の間隔」) |

    無効な定義は古い定義で、`tools/list` にも `tools/call` の判定にも `.d.ts` (7.2 節) にも使わない。
  - `shared` の子の定義は、接続したら取る。
- 世代番号:
  - 単位ごとに 1 つ。次のときに、その単位の世代番号を 1 つ増やす:
    - その単位の接続で、子の `list_changed` を受けた。
    - その単位の接続が切れた。
  - 単位が在る間は、接続を作り直しても世代番号を引き継ぐ。
  - 切断の後:
    - 確立するまでは子へ要求を送れず、取得を始められない。SDK は、閉じた接続で `connect` し直すまで要求を拒否する (7.2 節の SDK の契約)。
    - 切れる前の接続で始めた取得の定義は、保持しない (下の終わり方の表)。SDK は、切断の時に応答を待っている要求を全部拒否する (7.2 節の SDK の契約)。
    - そのため、再接続して取り直すまで、その子のツールは公開しない。
- 取得: 単位の定義を子から取る 1 つの処理。次の手順で行う:
  1. 単位の今の世代番号を読む。
  2. 子へ `tools/list` を送り、応答を待つ。
  3. 成功し、応答を受けた時の世代番号が 1 で読んだものと違えば (世代番号の食い違い):
     - 1 回目の食い違い: 1 に戻って、もう 1 回行う。
     - 2 回目の食い違い: 下の終わり方の表の「世代番号の食い違いが 2 回続いた」で終わる。

  終わり方ごとの扱い:

  | 終わり方 | 扱い |
  | --- | --- |
  | 成功し、応答を受けた時の世代番号が、送る前に読んだものと同じ | 定義を保持し、使う |
  | 世代番号の食い違いが 2 回続いた | 定義を保持しない。取り直せなかった定義として扱う |
  | 失敗 (例外で抜けたものを含む)・子への要求の応答を待つ上限 (7.2 節)・接続の切断 | 取り直せなかった定義として扱う。切断なら、接続が確立するまで次の取得を始められない (上) |

  - 取得は、単位ごとに同時に 1 つまで。進行中の取得は、表 1 つで持つ:
    - 鍵: 単位
    - 値: 取得 (終わりを待てるもの) と、取得を始めた要求の利用者 (`iss`, `sub`)。利用者を値に持つのは、取得の途中でトークンの行が消えても数えるため。
  - 表への登録は、取得の最初に 1 回。同じ単位の取得が進行中なら、後から来た要求は取得を始めず、表のその単位の取得の終わりを待つ。進行中かの確認から登録までの間に、await を挟まない (`per_user` の子では、その間に 3.3 節の上限の数も数える)。
  - 3.3 節の取り直しの上限は、この表から数える:
    - 全体の数: 表の要素のうち、鍵が `per_user` の子の単位 (子のトークンの id) のものの数。
    - 利用者ごとの数: そのうち、値の (`iss`, `sub`) がその利用者のものの数。
    - 検査を受ける取得と、複数の単位を登録する順は、3.3 節の「上限の扱い」。
  - 取得は、どの終わり方でも、finally で次の順に行う。間に await を挟まない:
    0. その単位の記録を、終わり方で置く。ただし、その単位が取得の途中で捨てられていれば (3.3 節の「定義を捨てるとき」。世代番号が無い)、記録を置かず、この取得の終わりではクライアントへの `list_changed` も出さない:
       - 定義を保持した: 定義。
       - 失敗か、子への要求の応答を待つ上限: 失敗の後の間隔 (下)。
       - 世代番号の食い違いが続いた・接続の切断: 置かない。
    1. 終わりを待っている要求へ、値を渡す:
       - 定義を保持し、0 で記録を置いた: その定義。
       - 他: 取り直せなかった定義。
    2. 表から、その単位を外す。
- 取り直す時期 (`shared` の子と `per_user` の子の両方に当てる):

  | 定義 | 取り直す時 |
  | --- | --- |
  | 古い定義と、まだ取っていない定義 | それを使う次の要求 (`tools/list`・`tools/call`。`gateway__run_code` を含む) |
  | 取り直せなかった定義 | それを使う次の要求。ただし、今の世代番号を持つ失敗の後の間隔の記録があれば、その間隔が過ぎた後の、それを使う最初の要求 |
  | 子との接続が切れている間の定義 | 接続が確立した後の、それを使う次の要求。`shared` の子は、接続したら取る (上) |

  - `per_user` の子の取得は、取り直しの上限 (3.3 節) の範囲で始める。
  - 1 つの要求が複数の単位の定義を取り直すとき (`tools/list` など)、始めた取得は並行に行う。1 つの子の待ちが、他の子の取得の待ちに足されない。
  - 子が応答しない間、間隔が過ぎた後の取得と、その取得の終わりを待つ要求は、子への要求の応答を待つ上限 (7.2 節) まで待つ。
- 失敗の後の間隔:
  - 単位の記録に置く (上の finally の 0)。
  - 間隔の間 (間隔の記録が有効で、間隔が過ぎていない間) にその定義を使う要求は、取り直せなかった定義として扱う。
  - 間隔が終わるとき:
    - 間隔が過ぎた。
    - 世代番号が変わった。記録は書き換えず、上の「記録の有効」で無効になる。
    - 取得が成功し、定義を保持した。finally の 0 が、記録を定義で置き換える。
  - 間隔は指数バックオフにする (上の再接続と同じ形)。今の世代番号の間隔の記録の上で続けて失敗するたびに延び、上限で止まる。記録が無効になるか置き換わった後の失敗は、初めの値から数える。初めの値と上限は固定値で、11 節の実測 7 の結果から決める。
  - 間隔の指数バックオフと、進行中の取得の表 (同じ単位の取得の終わりを待ち合わせる) に当たる機能が、SDK v2 の client (2.4.0) と deno の標準に無いかは未確認。実装の前に確かめる。
  - 取り直せなかった定義の取り直し方の比較。物差し:
    - 取得の回数
    - 取得が乗る経路
    - 伝わる古さ (子が戻ってから、定義が取れるまで)

    | 案 | 取得の回数 | 取得が乗る経路 | 伝わる古さ | 採否 |
    | --- | --- | --- | --- | --- |
    | 毎要求で取る | 子が戻るまで、その定義を使う要求ごとに 1 回 | 全部の要求。子が応答しなければ、その定義を使う要求がどれも応答の上限まで待つ | 0 (戻った後の最初の要求) | 採らない。応答しない子 1 つが、それを使う要求の全部を、応答の上限まで遅らせる |
    | 失敗の後に指数バックオフの間隔を置く | 間隔ごとに 1 回。間隔は続けて失敗するたびに延び、上限で止まる | 間隔が過ぎた後に、その定義を使う最初の要求 | 多くて間隔の上限 | 採る。子が応答しない間の取得の回数と、応答の上限まで待つ要求の数が、間隔で抑えられる。再接続と同じ形。管理対象は、単位ごとの間隔 (単位の記録の一部) と固定値 2 つ (初めの値と上限) だけ増える。毎要求で取る案は管理対象を増やさないが、応答しない子 1 つがそれを使う要求の全部を遅らせるので、この増分を払う |
    | 失敗を一定時間保持する | 保持の時間ごとに 1 回 | 保持が過ぎた後に、その定義を使う最初の要求 | 多くて保持の時間 | 採らない。保持の時間を指数バックオフの間隔の上限と同じにすると、伝わる古さは同じで、長く続く失敗での取得の回数は指数バックオフのほうが少ない |

- クライアントへの `list_changed` (変化ごとに一覧へ届く経路は、2 節の表):
  - 出す時:
    - 子の `list_changed` を受けた時 (上の世代番号の更新)。取り直しの成否によらない。
    - 子との接続が切れて、その単位の定義を公開から外した時 (切断で世代番号を増やした後)。
    - 取り直せず、その単位の定義を公開から外した時。次の両方を満たすとき:
      - 取得が失敗か応答の上限で終わった。
      - その前の記録が、今の世代番号を持つ定義 (寿命が過ぎたものを含む) だった。

      前の記録が他 (今の世代番号を持つ失敗の後の間隔・前の世代番号の記録・記録なし) なら、その定義は、前の失敗か子の `list_changed` か切断の時から、あるいは初めから公開していない。そのときの `list_changed` は、上の行で出ている。
    - その単位の取得が成功し、定義を保持した時 (上の終わり方の表の 1 行目)。子の `list_changed` を受けた後の取得も含む。

    取得の終わりで出す 2 つ (取り直せず外した時と、成功した時) は、finally の 0 で記録を置いた時だけ出す。
  - 送る相手は、その単位の定義を一覧に使う接続:
    - `shared` の子: その子を使える利用者 (server の `groups`。5.1 節) の全接続。
    - `per_user` の子: そのトークンの利用者の接続。
  - 相手ごとに 1 件ずつ独立に送る。1 件の送信が失敗したときも、残りへの送信は続ける。
  - 取得の成功で出す理由: 成功する前は、その単位に使える定義が無い。そのため、クライアントの一覧は、そのツールを欠くか古い。使える定義が無いのは、次のどれか:
    - 取り直せなかった定義
    - 寿命が過ぎて古くなった定義
    - 子の `list_changed` か切断で古くなった定義
    - まだ取っていない
  - 子の `list_changed` を受けた時と、その後の取得の成功で、2 回出ることがある。2 回目は、クライアントに一覧の取り直しを余分に 1 回させる。
  - 寿命の取り直しの成功での出し方の比較。物差し:
    - 中身が変わらないときの通知
    - 保持する状態
    - 2025 系のクライアントの一覧 (2 節。クライアントが `list_changed` に応じて取り直すかは未測定)

    | 案 | 変わらないときの通知 | 保持する状態 | 2025 系の一覧 | 採否 |
    | --- | --- | --- | --- | --- |
    | 毎回出す | 寿命 1 つ分の時間あたり、相手 (接続) ごとに多くて 1 回。`shared` の子では、その子を使える利用者の接続の数だけ送る | 増やさない | 子が `list_changed` を送らずに変えた定義も、通知で取り直される | 採る。出す条件を増やさずに、2025 系の一覧にも子の変化が届く |
    | 中身が変わったときだけ出す | 出さない | 増やさない。前の記録は、取得の終わりに置き換えるまで残る (上の「記録の有効」) | 変わった定義は、通知で取り直される | 採らない。出す条件に、前の記録の定義との比べ (定義の列の等しさの規則) が加わる。得るのは、変わらないときの通知の削減 (寿命 1 つ分の時間あたり、接続の数の分) で、量は見積もっていない |
    | 出さない | 出さない | 増やさない | 子が `list_changed` を送らずに変えた定義が、クライアントが取り直すまで届かない | 採らない |

- 取り直せなかった定義のツール:
  - `tools/call` は、`isError: true` と、取り直せなかった原因で決まる理由 (6.2 節) を返す:
    - `busy_refetch`: `per_user` の子で、取り直しの上限 (3.3 節) で取得を始められなかった。
    - `child_unreachable`: 他の全部。次のどれか:
      - 取得が、失敗・子への要求の応答を待つ上限・接続の切断で終わった。
      - 世代番号の食い違いが 2 回続いた。
      - 失敗の後の間隔の間。
      - 子との接続が切れていて、取得を始められない。
  - 古い定義で答えない。
  - `tools/list` での出し方は、下の比較で決める。
- 取り直せなかった定義のツールの、`tools/list` での出し方の比較。物差し:
  - 一時的な失敗として利用者に伝わるか
  - 定義の状態の数
  - 同じ一覧の他のツール
  - 依存するクライアントの挙動
  - 子の存在が一覧に出るか

  | 案 | 一時的な失敗として伝わるか | 定義の状態の数 | 同じ一覧の他のツール | 依存するクライアントの挙動 | 子の存在が一覧に出るか | 採否 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 載せない | 伝わらない。`tools/list` は成功として返り、ツールが欠けたことが一覧に現れない | 増やさない | 使える | モデルが、欠けたツールを「無い」と利用者に伝えない (未確認。11 節の実測 3) | 出ない | 実測 3 の結果まで保留。崩れないと分かったときだけ採る |
  | `tools/list` をエラーの応答で返す | 伝わる | 増やさない | 使えなくなる | 無い | 出ない | 採らない。1 つの子の失敗で、他の子のツールも取れなくなる |
  | 項目として載せる: 一時的に取れないことを示す項目にし、その `tools/call` は `isError: true` を返す | 伝わる | 1 つ増える (定義を持たない項目) | 使える | モデルが、項目の印を読んで利用者に伝える (未確認) | 出る。子のツールが全部 deny の利用者にも出る | 採らない。定義が無いので子のツール名が分からず、deny の規則 (5.1 節) を当てられない |

  - 実測 3 が崩れると (モデルが欠けたツールを「無い」と伝えると)、一時的な失敗が、ツールが無いこととして利用者に伝わる。崩れたら、次の順で行う:
    1. 実測 3 の結果を canon に足す。
    2. 「載せない」を採らず、この比較をやり直す。
    3. 上の「クライアントへの `list_changed`」の出す時のうち、切断と取り直せなかった時の 2 つと、2 節の表の「子との接続が切れた」「定義を取り直せなくなった」の行をやり直す。
  - 続く時間: 取り直しが成功するまで。成功したら、クライアントへ `list_changed` を出す (上)。取り直すのは、上の「取り直す時期」。
    - 取り直しは要求で起きる。2025 系では、間隔が過ぎた後も、クライアントが次に一覧か呼び出しを送るまで取り直されず、取り直しが成功すれば `list_changed` が出る (2 節)。
- 定義の最長の寿命 (`shared` の子の一覧と、`per_user` の子の定義の両方に当てる):
  - 世代番号が変わるのは、`list_changed` と切断のときだけ。子が `list_changed` を送らずに定義を変えたとき、古い定義を使う時間の上限 (古さの上限) は寿命で決まる。
  - 寿命が過ぎた定義は、上の「記録の有効」で古い定義になり、次にそれを使う要求で取り直す。
  - 寿命は固定値。
  - 寿命の機構の比較。どの案も、`list_changed` での取り直し (上) と併せて使う。物差し:
    - 古さの上限
    - 取得の回数
    - 取得が乗る経路

    | 案 | 古さの上限 | 取得の回数 | 取得が乗る経路 | 採否 |
    | --- | --- | --- | --- | --- |
    | 毎要求で取る | 0 (要求の時点の定義を使う) | 要求ごとに、使う子ごとに 1 回 | 全部の要求 | 採らない。取得の回数と時間が、要求の数に比例する |
    | 周期で取り直す | 周期 | 周期ごとに、定義ごとに 1 回。使われない定義も取る | 要求の外の、周期の処理 | 採らない。使われない定義も取り直し、周期の処理という管理対象が増える |
    | 接続時だけ取る | 無い (接続が続く間、変化を拾わない) | 接続ごとに 1 回 | 接続の確立 | 採らない。古さに上限が無い |
    | 寿命が過ぎたら次の要求で取る | 寿命 | 寿命 1 つ分の時間あたり、定義ごとに多くて 1 回。使われた定義だけ | 寿命が過ぎた後に、その定義を使う最初の要求 | 採る。古さに上限があり、使われない定義は取らない |

  - 値は、11 節の実測 5 の結果から、次の 2 つの兼ね合いで決める。寿命を短くすると、古さの上限は下がり、取得の回数は増える:
    - 取得の回数 (寿命 1 つ分の時間あたり、多くて):
      - `shared` の子: 子ごとに 1 回。
      - `per_user` の子: 子ごとに、定義を持つ利用者の数だけ (利用者数に比例する)。

      負荷は、これに取得 1 回の時間を掛けて見積もる。
    - 古さの上限: 寿命そのもの。
- stdio の子は全利用者で共有する 1 プロセスにする。利用者ごとに分けるのは範囲外。

| Code Mode の実行 (run) | run id。実行 (入れ子の run を含む) を始めるたびに、128 bit の乱数で振る。深さや連番から導かない (導くと別の run が同じ id になり、「この実行の間は許可」がその run に及ぶ) | id が一致 | 実行が終わるまで |
| 承認の記録の項目 | 種類ごと (下の表) | 同左 | 同左。どれも、中断した要求の記録より長くは残らない |
| 利用者の操作 (承認) | 操作 id (`op_` と 128 bit の乱数) | 記録が待ちで、送信の操作 id が、待ちの操作 id と一致する (6.3 節の「答え」)。ページの送信では、ページのログインの利用者が要求の利用者と一致することも要る | 中断した要求と同じ |
| ブラウザのセッション | cookie の値 | 署名が正しく、期限内 | 8 時間 |
| (将来) 利用者ごとの子のトークン | (`iss`, `sub`, server id) | 3 つが一致 | 失効か、利用者が切るまで (SQLite) |

承認の記録の項目の種類。項目を持つのは Code Mode の実行だけ。直接の呼び出しの承認は、記録の状態「答え済み」が持ち、項目を書かない (承認する呼び出しは記録の `name`・`arguments`。6.3 節)。種類は、選んだ選択肢 (6.1 節) で、次の 2 つ:

| 種類 | 鍵 | 通す呼び出し | 寿命 |
| --- | --- | --- | --- |
| Code Mode・今回だけ許可 | (run id, 公開名, 引数) | run id が一致し、呼び出し (上の表の「ツールの呼び出し」) が等しいもの | 一致した呼び出しを 1 回通すまで。通す時に項目を外す (6.3 節の「承認」) |
| Code Mode・この実行の間は許可 | (run id, 公開名) | run id と公開名が一致するもの (引数は見ない) | 承認した run の間。入れ子の別の run には及ばない (run id が違う) |

## 5. Policy (allow / ask / deny)

### 5.1 判定

1. 利用者が server の `groups` のどれにも入っていなければ、その server のツールは全部 deny。`groups` は必須 (4.1 節の起動時の検査)。
2. server の `rules` を上から見て、次の 2 つを両方満たす最初の規則の `decision` を採る:
   - `tools` (下の形の文字列か、その配列。配列なら、どれか 1 つが当たれば当たる) が当たる。
   - `groups` に利用者が入っている (`"*"` を含む)。
3. 当たる規則が無ければ、全体の `default` (既定は ask) を採る。

- `groups` の `"*"` は全員に当たる。
- rule の `tools` の文字列:
  - 形は `^[A-Za-z0-9_*-]+$`。形に外れる記述は、起動時に拒否する (4.1 節)。
  - `*` だけを任意の文字の並び (0 文字を含む) として扱い、他の文字はそのまま比べる。
  - 照合は子の名前 (子が報告した名前。例: `create_issue`) で行う。公開名 (例: `github__create_issue`) では当たらない。公開名の接頭辞で始まる記述は、起動時に拒否する (4.1 節)。
- 上から順に評価する理由: 「admins だけ ask、他は deny」のような例外を、否定を使わずに書ける。
- 判定は `groups` と `rules` だけで行う。仕様は tool annotations (`readOnlyHint` など) を信頼しない入力として扱うよう求めている。annotations はそのままクライアントへ渡す。

### 5.2 効果

| 判定 | `tools/list` | 直接の呼び出し | Code Mode の中 |
| --- | --- | --- | --- |
| allow | 載せる | 子へ中継する | 子へ中継する |
| ask | 載せる | 承認されたら中継する。拒否なら `denied`、取り消しか期限なら `cancelled` を、`isError: true` で返す (6.3 節) | 承認されたら中継する。拒否なら `denied`、取り消しか期限なら `cancelled` で、実行全体を止めて `isError: true` で返す (6.3 節) |
| deny | 載せない | 「ツールが無い」と同じエラーにする | 型定義に載せない。呼べば例外にする |

判定は、一覧を作るときと、呼び出しのたびの両方で行う。

## 6. 利用者の操作

### 6.1 操作の種類

| 種類 | 起きるとき | 利用者が見るもの |
| --- | --- | --- |
| 承認 | ask のツールが呼ばれた | server、tool、引数、呼んだクライアント。Code Mode なら run id と深さ、スクリプトの全文 |
| (将来) 接続 | `per_user` の子に、利用者のトークンが無い | 子の名前と、送られる先の AS のドメイン |

承認の選択肢:

- 今回だけ許可
- この実行の間は許可
  - Code Mode のときだけ出す。
  - 範囲は承認した run だけ (4.4 節)。
- 拒否

form で聞くときの既定の選択は「拒否」。

### 6.2 届け方

クライアントの能力ごとに、上の行から使えるものを選ぶ。

| クライアントの能力 | 承認 | (将来) 接続 |
| --- | --- | --- |
| elicitation の form と url | form で聞く | url で `/i/<id>` を開かせる |
| elicitation の form だけ | form で聞く | 結果に URL を返す (下) |
| elicitation の url だけ | 結果に URL を返す (下) | url で `/i/<id>` を開かせる |
| form も url も持たない | 結果に URL を返す (下) | 結果に URL を返す (下) |

- elicitation で聞く場合:
  - 2025 系: その場で `elicitation/create` を送って待つ。
    - 待つ時間には固定値の上限を置く。値は期限 (6.3 節) 以下で、実装で決める。上限は SDK の要求の `timeout` で渡す (7.2 節)。
    - 答えを受けたときと上限を過ぎたときの扱いは、6.3 節の状態遷移の表に従う。
  - 2026 系:
    1. `input_required` を返す。
    2. `requestState` には、要求 id と操作 id だけを入れる。署名はしない (下の「`requestState` の署名の要否」)。
       - `requestState` の寿命は、記録の寿命で決まる。記録は期限 (6.3 節) で消える。期限を持たない実行中は、7.2 節の上限で終わって、期限を持つ決定に移る。
       - 記録が消えれば、再開の確かめで `unknown` になる。
    3. 再開の確かめ: 要求 id の出どころは、次のどちらか:
       - 2026 系の再送: `requestState` から読む。
       - `gateway__resume` (下): `request_id` を使う。

       再送か `gateway__resume` の呼び出しを受けたら、次を全部確かめる。どれかが外れれば、`isError: true` と理由 `unknown` を返す。
       - 要求 id の記録 (6.3 節) がある。
       - 呼び出しの利用者が、記録の利用者と一致する。
       - 呼び出しのクライアントが、記録のクライアントと一致する。
       - 再送のとき、`name`・`arguments` が、記録のものと等しい (4.4 節の「ツールの呼び出し」)。

       `requestState` の操作 id は、ここでは確かめない。答えを受けるかを決める照合で使う (6.3 節の「答え」)。
    4. 再送を、6.3 節の状態遷移の表の「再開」の行で扱う。答えを運ぶ再送は、先に答えの事象 (6.3 節) の行で扱う。
  - `requestState` の署名の要否:
    - 仕様の求め (https://github.com/modelcontextprotocol/modelcontextprotocol の `docs/specification/2026-07-28/basic/patterns/mrtr.mdx` の Server Requirements (Basic Workflow)、2026-10-28):
      - サーバーは、`requestState` を攻撃者が操る入力として扱う。次のどれかに効くなら、完全性を守り (HMAC や AEAD など)、検証に外れたものを拒否する:
        - 認可
        - 資源の取得
        - 業務の論理
      - 完全性の保護を省いてよいのは、改ざんで起きうる最悪が要求の失敗のときだけ。
      - replay を防ぐため、守った payload の中に、下の表の「仕様が勧める項目」の 3 つを入れて、受けた時に確かめるよう勧める (SHOULD)。
    - このゲートウェイで、`requestState` を書き換えた再送に起きること:
      - 要求 id を書き換えた: 引いた記録で再開の確かめをする。記録で分かれる:
        - 別の利用者かクライアントの記録: `unknown`。
        - 同じ利用者とクライアントの記録で、`name`・`arguments` も等しい: その記録の再開になる。これは、クライアントがその記録の `requestState` を書き換えずに送ったときと同じ結果。

        クライアントが受けていない要求 id は 128 bit の乱数で (4.4 節)、推測できない。
      - 操作 id を書き換えた: 記録が待っている操作 id と一致しなければ、受けなかった答え (6.3 節) で、記録に何も書かない。
      - どちらも、要求の失敗か、書き換えずに送れる要求と同じ結果で終わる。
    - 仕様が payload に入れるよう勧める 3 つは、記録が持つ:

      | 仕様が勧める項目 | このゲートウェイでの持ち方 |
      | --- | --- |
      | 認証した利用者 | 記録の利用者。再開の確かめが、呼び出しの利用者と比べる |
      | 短い期限 | 記録の状態の期限 (6.3 節の「期限」)。過ぎた記録は消えている |
      | 元の要求の識別 (method と主な引数の digest など) | 記録の `name`・`arguments`。再開の確かめが比べる |
    - 比べた案。物差し:
      - 管理対象 (段・鍵)
      - 書き換えで起きうること

      | 案 | 管理対象 | 書き換えで起きうること | 採否 |
      | --- | --- | --- | --- |
      | JWS で署名する | 署名の段と検査の段が増える。署名の鍵が覆うものが 1 つ増え、鍵を替えると未決の再送が `unknown` になる | 署名に外れて `unknown` | 採らない。署名が変えるのは、書き換えた再送の結果が `unknown` になることだけで、書き換えずに送れる要求と同じ結果は変わらない。段と鍵の範囲だけが増える |
      | 署名しない | 増えない。記録を引いて確かめる段は、`gateway__resume` の `request_id` (これも署名しない) と同じもの | 要求の失敗か、書き換えずに送れる要求と同じ結果 (上) | 採る |

    - この判断は、上の「再開の確かめ」の項目が記録と比べるものに依る。確かめの項目を減らすときは、この比較をやり直す。11 節の 3 の試験で、書き換えた `requestState` の再送を確かめる。
- 結果に URL を返す場合:
  - 要求を中断し、ツールの結果として次を返す:
    - 何が必要か (承認か接続か)
    - `/i/<操作 id>` の URL
    - 再開に使う `request_id` (要求 id。`req_` で始まる。URL の操作 id は `op_` で始まる別の値)
    - 再開の仕方
  - モデルがチャットで URL を示し、利用者はブラウザで authentik にログインして操作する。
  - そのあと、モデルが `gateway__resume({ request_id })` を呼ぶ。上の 2026 系と同じ再開の確かめを通してから、6.3 節の状態遷移の表の「再開」の行で扱う。
    - `request_id` が `op_` で始まれば、記録を引かずに `isError: true` と理由 `request_id_is_operation_id` を返す。中断の時に返す結果には、URL (操作 id を含む) と `request_id` が並ぶ (上)。モデルが URL の操作 id を `request_id` に渡す誤りを、期限切れなどの `unknown` と分けて伝えるため。接頭辞だけを見るので、記録の有無は漏らさない。
  - `gateway__resume` が返すものは次のどれか。どれを返すかは 6.3 節の表で決まる:
    - 元の要求の結果
    - `pending`: `isError: false` で返し、元の要求は未完了として示す。どれも次を含む:
      - `status: "pending"`
      - `request_id` と再開の仕方 (`gateway__resume` を呼ぶ)

      加えて、記録の状態で決まる次のどちらか一方を含む:
      - 記録が待ち: 待っている操作の URL。
      - 記録が実行中で、待っているだけの要求の数が上限 (6.3 節の「上限」) に達している: `reason: "busy_waiting"`。この再開は待たせていない。実行は続いていて、後から再開すれば結果を引ける。
    - `isError: true` と理由 (下の表)
  - 2026 系の再送が、待っているだけの要求の上限に達したときも、同じ `pending` (`reason: "busy_waiting"`) をツールの結果として返す (6.3 節の「実行中・再開」の行)。モデルは、`pending` の `request_id` で `gateway__resume` を呼んで結果を引く。
  - `pending` は `isError: false` で返すので、クライアントのモデルが完了とみなすと、未完了の操作を完了として利用者に伝える。
    - claude.ai と Claude Code のモデルがそうしないかは未確認 (11 節の実測 3)。
    - この形は、実測 3 が済むまで、`pending` を返す実装の前提にしない。`pending` を返す実装:
      - `gateway__resume`
      - `busy_waiting` の 2026 系の再送
    - 実測 3 が崩れたら (モデルが `pending` を完了とみなしたら)、`pending` を返す上の 2 つの経路は作らない。実測 3 の結果を canon に足してから、この節の `gateway__resume` が返すものと、6.3 節の「実行中・再開」の行を書き直す。
  - 実行中のときに、待っているだけの要求の上限までは `running` を返さず待つ理由:
    - 待つのは実行中の間 (実行の終わりか次の中断まで) で、その時間は 7.2 節の上限で抑えられる (6.3 節の「期限」の、実行中の時間を抑える上限)。
    - 待つ要求の数は、記録ごとの上限 (6.3 節の「上限」) で抑えられる。
    - `running` を返すと、モデルが呼び直す経路と状態が 1 つ増え、`pending` と同じく、モデルが未完了を完了とみなすおそれ (上) も増える。上限を超えた再開に返す `pending` の `reason` は、状態を増やさない。
  - 安全性:
    - ページは、次を両方満たすときだけ答えを受ける (ページの確かめ):
      - ログインした利用者が、要求の利用者と一致する。
      - URL の操作 id が、記録が答えを待っている操作 id と一致する。
    - ページに出すものは、6.3 節の「答えを運んだものの続き」。受けた送信の結果はページに出さず、次の `gateway__resume` で返す。
    - 送信には CSRF の対策をする。
    - URL を持つだけでは何もできない。
    - モデルが URL を伝えなければ何も起きない (閉じる側に倒れる)。
- 対象のクライアント (0 節) のうち、claude.ai (Claude Desktop を含む) と ChatGPT は、「form も url も持たない」の行に当たると見込む (2026-10-27 の時点。claude.ai は anthropics/claude-ai-mcp#153 で対応が要望されている。確かめ方は 11 節の実測 3)。対応したら、上の表で form の行が自動で選ばれる。
- `isError` の使い分け:
  - `isError: false` (`pending`): 実行か待ちが続いていて、後から再開すれば結果を引ける。待っているだけの要求の数によらず、この旗にする。
  - `isError: true` (下の表の理由): 要求を受けないか、結果が終端で決まった。表の「分類」の列。
- `isError: true` の結果に入れる理由:

  | 理由 | 分類 | 返すとき |
  | --- | --- | --- |
  | `unknown` | 受けない | 再開の確かめ (上の 2026 系) のどれかが外れた (期限で消えた id を含む) |
  | `denied` | 終端 | 拒否の答え (6.3 節) か、再開の直前の判定 (6.3 節) の deny で、結果が決まった |
  | `cancelled` | 終端 | 6.3 節の「結果を `cancelled` にするもの」で、結果が決まった |
  | `result_too_large` | 終端 | 決まった結果が、記録 1 件の大きさの上限を超えた (6.3 節の「上限」) |
  | `child_timeout` | 終端 | 直接の呼び出しで、子へ送った `tools/call` の応答を待つ上限 (7.2 節) を過ぎた (6.3 節の事象「完了」) |
  | `child_unreachable` | 受けない | 取り直せなかった定義のツールを呼んだ。`busy_refetch` との分け方は 4.3 節の「取り直せなかった定義のツール」 |
  | `request_id_is_operation_id` | 受けない | `gateway__resume` の `request_id` が `op_` で始まる (上) |
  | `code_too_large` | 受けない | `gateway__run_code` の `code` が、7.1 節の入力の上限を超える。実行を始める前に断る |
  | `arguments_too_large` | 受けない | 中断の時に、元の要求の `name`・`arguments` が、記録 1 件の大きさの上限 (6.3 節) を超えていて、新しい中断を作れない |
  | `busy_suspended` | 受けない | 中断した要求の数が、利用者ごとか全体の上限 (6.3 節) に達していて、新しい中断を作れない。記録は、結果だけになっても期限 (6.3 節) で消えるまで数えるので、すぐに再試行しても減らないことがある |
  | `busy_runs` | 受けない | 同時に動く Code Mode の実行の数が、利用者ごとか全体の上限 (7.2 節) に達していて、新しい実行を始められない。実行が終われば減る |
  | `busy_refetch` | 受けない | (将来) 取り直せなかった定義のツールを呼び、その原因が取り直しの上限 (3.3 節) だった。分け方は 4.3 節の「取り直せなかった定義のツール」。上限が数える取得が終われば、再試行で通りうる |

- Code Mode の実行の `denied`・`cancelled` にも、7.1 節の `calls` を入れる。止めるまでに起きた副作用を、モデルが知るため。

### 6.3 中断の扱い

- 中断した要求は、メモリに記録として持つ。記録が持つもの:
  - 利用者・クライアント
  - 状態 (下の状態遷移の表)。状態の値は、状態ごとのもの (待っている操作 id、期限など) を含む (下の「状態」)。
  - 元の `tools/call` の `name`・`arguments`。中継する server と tool は、`name` を 4.2 節の最初の `__` で分けて得る。
  - Code Mode の実行なら、Promise を待ったまま止めた worker (入れ子の run (7.3 節) の worker を含む)。
  - 承認:
    - 直接の呼び出し: 状態「答え済み」が承認を表す。承認する呼び出しは、記録の `name`・`arguments` の 1 つ。項目は書かない。
    - Code Mode の実行: 承認の記録 (承認された呼び出しごとの項目の列) を持つ。項目の種類と、それぞれの鍵・等しさ・寿命は 4.4 節の「承認の記録の項目」。
    - 承認の根拠は、記録の次のものに固定する:
      - 公開名
      - 引数
      - クライアント
      - run id (Code Mode のとき)
    - Code Mode で承認で通すのは、実行する呼び出しが承認の記録の項目のどれかに当たるときだけ。照合は次の順に行う:
      1. 「今回だけ許可」の項目を探す。当たれば 1 つを列から外してから、その呼び出しを実行する。外すことと子への中継を始めることの間に、await を挟まない。挟むと、同じ項目に当たる 2 つ目の呼び出しも通る。
      2. 1 で当たらなければ、「この実行の間は許可」の項目に当たるかを見る。当たれば、外さずに通す。
  - 結ばれた要求 (下)
  - 結果 (決まったら)。次のどれか:
    - 元の要求の結果
    - `denied`
    - `cancelled`
- 結ばれた要求: 記録について、ゲートウェイがまだ応答を返していない要求。役で 2 つに分ける:
  - 実行を始めた要求: 1 つの記録に多くて 1 つ。次のどちらか:
    - 状態を「実行中」にした要求 (「答え済み・再開」の行)。
    - 2025 系の元の要求のうち、操作をその場の `elicitation/create` で聞くもの。待ちの間も結ばれたまま残る。
  - 待っているだけの要求: 実行中に来た再開で、実行の終わりか次の中断を待つもの。数には上限がある (下の「上限」)。
  - 状態ごとの結ばれた要求:

    | 状態 | 実行を始めた要求 | 待っているだけの要求 |
    | --- | --- | --- |
    | 待ち | 2025 系の元の要求だけ。他の経路の要求には、操作を届けた時に応答を返している | 無い。実行中から待ちに移る時に、全部に応答を返している |
    | 答え済み | 無い (下の「順序」) | 無い |
    | 実行中 | 多くて 1 つ。切断で外れる | 上限まで |
    | 決定 | 無い。決定に移る時に、全部に応答を返している | 無い |

  - 結ばれた要求への返し: 1 つの事象で結ばれた要求へ返すものは、1 件ずつ独立に返す。
    - 返すもの:
      - 結果
      - 待ちを知らせる形
      - `cancelled`
    - 1 件の送信が失敗したときも、残りへの返しは続ける。
    - 状態遷移の表で結ばれた要求へ返す行は、これに従う。
  - 返し先の無い記録: 結ばれた要求が無く、要求 id をクライアントに渡していない記録。結果を引く要求も、答えを運ぶ要求も来ない。
    - 操作をその場の `elicitation/create` で聞く記録 (2025 系) は、要求 id をクライアントに渡さない (6.2 節の「elicitation で聞く場合」)。そのため、元の要求が切断で外れると、状態によらず返し先の無い記録になる。
    - 他の経路の記録は、操作を届ける時に要求 id を渡す (2026 系の `requestState` と、結果に返す `request_id`。6.2 節)。そのため、返し先の無い記録にならない。
    - 状態遷移の表は、返し先の無い記録を消す。消す行:
      - 待ち・切断 (実行を始めた要求)
      - 実行中・中断
      - 実行中・完了
    - 実行中に切断した記録 (「実行中・切断 (実行を始めた要求)」の行) は、実行が中断か完了するまで残す。実行が承認の記録を使うため。残る間は、中断の上限の枠を占める。
- 答え: 操作への答えを運ぶ 1 回の送信。経路で違うのは、受ける前の確かめだけ。送信の経路:
  - 2026 系の再送
  - 2025 系の、その場の `elicitation/create` への応答
  - ページの送信
- 送信を受けるのは、次を全部満たすときだけ:
  - 経路ごとの確かめを通った:
    - 2026 系の再送: 再開の確かめ (6.2 節)。
    - ページの送信: ページの確かめ (6.2 節)。
    - 2025 系: その操作で送った `elicitation/create` への応答である (SDK が要求の id で結ぶ)。
  - 記録が待ちで、送信の操作 id が、待ちの操作 id と一致する。記録が待ちでなければ、照合する操作 id が無いので、この条件は外れる。
  - 操作の呼び出しの全部に答えがある。
- 呼び出しごとの答えの分類 (elicitation の `action` の意味を決めるのは、この表だけ):

  | 答え | 分類 |
  | --- | --- |
  | `action: "accept"` で「今回だけ許可」か「この実行の間は許可」。ページの同じ選択肢 | 許可 |
  | `action: "accept"` で「拒否」、`action: "decline"`、ページの「拒否」 | 拒否 |
  | `action: "cancel"` (利用者が選ばずに閉じた) | 取り消し |

  `action: "decline"` と `action: "cancel"` は、その elicitation に載せた呼び出しの全部への答えとする。
- 受けた送信の答えは、呼び出しごとの答えから次で決める:
  - 全部が許可: 許可。
  - 1 つでも拒否: 拒否。
  - 拒否が無く、1 つでも取り消し: 取り消し。

  拒否と取り消しのどちらでも、同じ送信の中の許可の呼び出しも実行しない。拒否を先に見るのは、利用者が明示した意思を結果の理由 (`denied`) に残すため。
- 受けなかった送信は、記録に何も書かない。外れた条件で次の 3 つに分ける。状態遷移の表の事象になるのは、初めの 2 つ:
  - 欠けた答え: 答えの無い呼び出しがあり、他の 2 つの条件は満たす。同じ操作を求め直す (下の「答えを運んだものの続き」)。仕様は、足りない入力を `input_required` で求め直すよう勧める (下の出典の `mrtr.mdx`)。
  - 受けなかった答え: 経路ごとの確かめは通り、操作 id の照合に外れた。古い操作への答えと、同じ操作への 2 回目の答えは、ここに入る。ページの送信では、ページの確かめに外れたものもここに入る (ページの確かめは操作 id の照合を含む)。
  - 2026 系の再送で、再開の確かめに外れた: `unknown` を返す (6.2 節)。
- 取り消しの形 (処理中の要求を取り消すときに、仕様が定める形。ゲートウェイが子へ伝えるときも同じ。7.2 節):
  - 2025 系: `notifications/cancelled`。
  - 2026 系:
    - Streamable HTTP: 応答の SSE の流れを閉じる。
    - stdio: `notifications/cancelled`。
- 結果を `cancelled` にするもの (これで全部):
  - 取り消しの答え (上の分類)。
  - 待ちの上限 (6.2 節)。
  - 期限 (下)。
  - 実行を始めた要求の、クライアントによる取り消し。待っているだけの要求の取り消しは、その要求が待つのをやめるだけ。
  - 実行の開始の失敗 (「答え済み・再開」の行)。
- 出典 (https://github.com/modelcontextprotocol/modelcontextprotocol の `docs/specification/`、2026-10-28 に確認):
  - elicitation の 3 つの action: `2025-11-25/client/elicitation.mdx` と `2026-07-28/client/elicitation.mdx` の Response Actions
  - 2025 系の取り消し: `2025-11-25/basic/utilities/cancellation.mdx`。`2025-11-25/basic/transports.mdx` の Streamable HTTP は、切断を取り消しと解釈すべきでないと書く。
  - 2026 系の取り消し: `2026-07-28/basic/patterns/cancellation.mdx` の Transport-Specific Cancellation。Streamable HTTP の切断を取り消しとして扱うことを求める。
  - 取り消された要求に応答しないことと、取り消しが応答の後に届きうること: 上の 2 つの `cancellation.mdx` の Behavior Requirements と Timing Considerations。
  - `2026-07-28/basic/patterns/mrtr.mdx`:
    - クライアントが再送するとは限らないこと: Server Requirements (Basic Workflow)。再送が来ない記録は、期限で消える (下の「期限」)。
    - 足りない入力を `input_required` で求め直すよう勧めること: Error Handling。
- 状態遷移の表: 中断した要求の扱いは、この表で決める。
  - 状態:

    | 状態 | 意味 |
    | --- | --- |
    | 待ち | 操作の答えを待っている。状態の値は、待っている操作 id と期限を含む。Code Mode の worker は guest の job を回さない。子の応答は deferred に届き、guest が受けるのは実行中に戻ってから |
    | 答え済み | 許可の答えを承認の記録に書き、実行を始めていない。状態の値は期限を含む。worker は待ちと同じく guest の job を回さない |
    | 実行中 | 再開の直前の判定を通って実行している。期限を持たない |
    | 決定 | 結果が決まった。worker と元の要求を捨て、結果と期限だけを持つ。結果が記録 1 件の大きさの上限を超えたときに持つものは、下の「上限」 |

  - 事象:
    - 中断: 呼び出しの判定が ask になり、承認 (上の「承認」) が無い。
      - 直接の呼び出し: 記録を作る最初の判定でだけ起きる。
      - Code Mode: worker が guest の job を回し終えた時点で、そういう呼び出しが 1 つ以上残り、実行が完了していない。その回に起きたものを 1 つの操作にまとめる (下の「同時に起きた ask」)。完了していれば事象は「完了」で、残った呼び出しは実行しない。
    - 答えの事象: 送信 (上の「答え」) で起きる、次の事象:
      - 受けた送信。送信の答えで 3 つに分かれる:
        - 答え (許可)
        - 答え (拒否)
        - 答え (取り消し)
      - 受けなかった送信 (上):
        - 欠けた答え
        - 受けなかった答え
    - 再開: 次のどちらか。
      - 再開の確かめ (6.2 節) を通った、2026 系の再送か `gateway__resume`。
      - 答えの事象の後に、答えを運んだ要求が続けて進むこと (下の「答えを運んだものの続き」)。
    - 取り消し (実行を始めた要求)・取り消し (待っているだけの要求): その役の結ばれた要求の、クライアントによる取り消し (上の「取り消しの形」)。取り消された要求には応答しない (上の出典)。
    - 切断 (実行を始めた要求)・切断 (待っているだけの要求): 2025 系の、その役の結ばれた要求の応答の流れが切れた。答えを待っている 2025 系の元の要求も含む。2025 系の仕様は切断を取り消しと解釈すべきでないとする (上の出典) ので、取り消しとは別の事象にする。2026 系の切断は取り消しに当たる。
    - 待ちの上限: 2025 系のその場の `elicitation/create` の応答を待つ上限 (6.2 節) を過ぎた。
    - 子の待ちの上限: Code Mode の中の呼び出しで、子への要求 1 件の応答を待つ上限 (7.2 節) を過ぎた。直接の呼び出しで過ぎたときは「完了」に入る。
    - 完了: 実行が終わった。終わり方:
      - 直接の呼び出し: 子へ送った `tools/call` の応答を受けたか、その応答を待つ上限 (7.2 節) を過ぎた。過ぎたときの結果は、`isError: true` と理由 `child_timeout` (6.2 節)。
      - Code Mode: 次のどれか。
        - 正常に終わった
        - `ToolError` で終わった
        - 7.2 節の上限で止まった (子への要求の応答を待つ上限を除く)
    - 期限: 今の状態の期限 (下の「期限」) を過ぎた。
  - 答えを運んだものの続き: 答えの事象 (上) の行の後に、答えを運んだものがすること。

    | 答えを運んだもの | 事象 | 続き |
    | --- | --- | --- |
    | 2026 系の再送 | 答え・欠けた答え・受けなかった答え | 事象の後の状態の「再開」の行で扱う |
    | 2025 系の元の要求 | 答え・欠けた答え | 事象の後の状態の「再開」の行で扱う |
    | ページの送信 | 答え | 受け付けたことと、結果は次の `gateway__resume` で返すことを、ページに出す |
    | ページの送信 | 欠けた答え | 同じページを出し直す |
    | ページの送信 | 受けなかった答え | 「この操作は済んでいるか期限切れ」をページに出す |

    2025 系の元の要求の事象が、答えと欠けた答えだけである理由: `elicitation/create` の応答が届くのは、その操作の答えを待っている間だけ。待ちを他の事象で出る時は abort し (下の「後始末」)、abort した要求に遅れて届いた応答は、ゲートウェイの待ちに渡らない (7.2 節の SDK の契約)。
  - 待ちを知らせる形: 記録が待ちにあるか待ちに移るときに、結ばれた要求へ返すもの。

    | 要求 | 返すもの |
    | --- | --- |
    | `gateway__resume` | `pending` (6.2 節) |
    | 2026 系の再送 | 待っている操作を求める `input_required` |
    | 2025 系の元の要求 | 応答を返さず、待っている操作をその場の `elicitation/create` で聞く。要求は結ばれたまま残る |

  - 遷移。行を「状態・事象」で呼ぶ。
    - 「起きない」は、その状態ではその事象が来ないことを示す。その行の「すること・返すもの」は「なし」で、括弧に来ない理由を書く。理由は、次のどれかを指す:
      - 結ばれた要求の表: その状態に、その役の結ばれた要求が無い (上の「状態ごとの結ばれた要求」)。
      - 状態の定義: 待ちと答え済みの間、worker は guest の job を回さない (上の「状態」)。
      - 受ける条件: 送信を受けるのは待ちだけ (上の「送信を受けるのは」)。待ちでない記録への送信は「受けなかった答え」。
      - 待ちの上限の範囲: 待ちの上限は、待ちの間に送る `elicitation/create` にだけ掛かる (上の事象「待ちの上限」)。
      - 後始末: 決定に移る時の後始末 (下) で、worker を止め、子への要求と `elicitation/create` の待ちを捨てている。
      - 期限の無い状態: 実行中は期限を持たない (上の「状態」)。
    - 「次の状態」の欄の括弧は、移った先の状態の期限の名前 (下の「期限」)。「変えない」は、状態も期限も変えない。

    記録が無いとき (中断で作る):

    | 事象 | 条件 | 次の状態 | すること・返すもの | 解放するもの |
    | --- | --- | --- | --- | --- |
    | 中断 | 元の要求が、記録 1 件の大きさの上限 (下の「上限」) を超える | (記録なし) | 記録を作らずに `arguments_too_large` を返す | — |
    | 中断 | 大きさの上限は超えず、数の上限 (下の「上限」) に達している | (記録なし) | 記録を作らずに `busy_suspended` を返す | — |
    | 中断 | どちらの上限にも当たらない | 待ち (新しい期限) | 記録を作り、操作を届ける (6.2 節) | — |

    記録が無いときの他のもの:
    - 2026 系の再送と `gateway__resume`: 再開の確かめで外れ、`unknown` を返す (6.2 節)。

    - 他の事象: 起きない。

    | 中断 | 返し先の無い記録 (上) でない | 待ち (新しい操作 id。新しい期限) | 結ばれた要求に、待ちを知らせる形で返す (上の「結ばれた要求への返し」)。Code Mode だけで起きる (上の事象「中断」) | — |

    | 答え (許可) | — | 起きない | なし (受ける条件) | — |
    | 答え (拒否) | — | 起きない | なし (受ける条件) | — |
    | 答え (取り消し) | — | 起きない | なし (受ける条件) | — |
    | 欠けた答え | — | 起きない | なし (受ける条件) | — |
    | 受けなかった答え | — | 変えない | 答えを運んだものの続きへ進む | — |
    | 再開 | 待っているだけの要求の数が、上限 (下) より少ない | 変えない | この要求は、待っているだけの要求になる。応答は、実行の終わりか次の中断の行で返す | — |
    | 再開 | 待っているだけの要求の数が、上限に達している | 変えない | 待たずに `pending` (`reason: "busy_waiting"`。6.2 節) を返す (下の「上限」) | — |
    | 取り消し (実行を始めた要求) | — | 決定 (`cancelled`。新しい期限) | 待っているだけの要求に `cancelled` を返す (上の「結ばれた要求への返し」)。取り消された要求には応答しない | 後始末 |
    | 取り消し (待っているだけの要求) | — | 変えない | その要求は待つのをやめる。応答はしない。実行は続く | — |
    | 切断 (実行を始めた要求) | — | 変えない | 実行は続ける (取り消しではない)。この要求は結ばれた要求から外れる (返し先の無い記録になるかは、上の「返し先の無い記録」) | — |
    | 切断 (待っているだけの要求) | — | 変えない | その要求は待つのをやめる。実行は続く | — |
    | 待ちの上限 | — | 起きない | なし (待ちの上限の範囲) | — |
    | 子の待ちの上限 | — | 変えない | その呼び出しが、guest の中で例外になる | その子への要求。SDK が子へ取り消しを伝える (7.2 節) |

    | 完了 | 返し先の無い記録でない。結果が上限を超える | 決定 (`result_too_large`。下の「上限」。新しい期限) | 結ばれた要求に結果を返す (上の「結ばれた要求への返し」) | 後始末 |
    | 完了 | 返し先の無い記録 | (記録なし) | 結果を捨てる。結果を引く要求は来ない (上の「返し先の無い記録」) | 後始末。記録を消す |
    | 期限 | — | 起きない | なし (期限の無い状態) | — |

    決定:

    | 事象 | 条件 | 次の状態 | すること・返すもの | 解放するもの |
    | --- | --- | --- | --- | --- |
    | 中断 | — | 起きない | なし (後始末) | — |
    | 答え (許可) | — | 起きない | なし (受ける条件) | — |
    | 答え (拒否) | — | 起きない | なし (受ける条件) | — |
    | 答え (取り消し) | — | 起きない | なし (受ける条件) | — |
    | 欠けた答え | — | 起きない | なし (受ける条件) | — |
    | 受けなかった答え | — | 変えない | 答えを運んだものの続きへ進む | — |
    | 再開 | 記録が結果を持つ | 変えない | 記録の結果を返す | — |
    | 再開 | 記録が理由 `result_too_large` だけを持つ | 変えない | `isError: true` と理由 `result_too_large` を返す (6.2 節) | — |
    | 取り消し (実行を始めた要求) | — | 変えない | 何もしない (結ばれた要求の表)。取り消しは応答の後に届きうる (上の出典) | — |
    | 取り消し (待っているだけの要求) | — | 変えない | 「決定・取り消し (実行を始めた要求)」と同じ | — |
    | 切断 (実行を始めた要求) | — | 変えない | 何もしない (結ばれた要求の表) | — |
    | 切断 (待っているだけの要求) | — | 変えない | 「決定・切断 (実行を始めた要求)」と同じ | — |
    | 待ちの上限 | — | 起きない | なし (後始末) | — |
    | 子の待ちの上限 | — | 起きない | なし (後始末) | — |
    | 完了 | — | 起きない | なし (後始末) | — |
    | 期限 | — | (記録なし) | 下の「期限」 | 記録を消す |

  - 順序:
    - 状態は、事象を受けた時に、await を挟まずに書き換える。同時に来た事象は、先に受けたものが書き換えた後の状態で扱う。例: 「答え済み」に 2 つの `gateway__resume` が同時に来たら、実行を始めるのは最初の 1 つだけで、2 つ目は「実行中・再開」の行で待つ。
    - 答えの事象と、それに続く「再開」の行は、間で await を挟まずに続けて扱う。「再開」の行が含む再開の直前の判定と、「今回だけ許可」の項目を外すことも同じ。そのため、答え済みに結ばれた要求は無い。
    - 結果を決める事象 (決定でない状態で、次の状態が「決定」か「(記録なし)」の行の事象) は先勝ち。結果が決まった後に来たものは、結果を変えない。
    - 「決定・期限」は、結果を変えずに記録を消す (下の「期限」)。
  - 後始末で止める・捨てるもの:
    - Code Mode の worker: 7.2 節の後始末を通して止める。
    - 子へ送って応答を待っている要求: 待ちを捨てる。SDK の要求の `signal` を abort すると、SDK が子へ取り消しを伝える (7.2 節)。遅れて届いた応答は使わない。
    - 2025 系のその場の `elicitation/create` の待ち: 同じく abort する。SDK がクライアントへ取り消しを伝える。
    - 元の要求 (`name`・`arguments`) と承認の記録。記録には結果だけを残す (「(記録なし)」に移る行では、記録ごと消す)。
- 再開の直前の判定: 「答え済み・再開」の行で、実行の直前に 5.1 節の判定をやり直す。
  - 再開は、次の経路の全部で同じに扱う。経路:
    - 2026 系の再送
    - `gateway__resume`
    - 2025 系のその場 (許可の答えを運んだ元の要求)
  - 判定する対象は、中断した要求の呼び出しの全部 (承認で止まったものも、(将来) 接続で止まったものも):
    - 直接の呼び出し: 記録の `name`
    - Code Mode: worker の中で止まっている呼び出し
  - 判定に使うのは、再開を求めた要求のトークンの `groups` (access token の claim。3.1 節)。再開を求めた要求は、上の経路のそれぞれで次のもの:
    - 2026 系の再送: その再送
    - `gateway__resume`: その呼び出し
    - 2025 系のその場: 元の要求
  - 対象の判定から、次の状態を決める:
    - どれかが deny: deny。
    - deny が無く、どれかが ask で、承認が無い: 承認を求め直す。新しい操作 id を振り、承認の無い呼び出しだけを 6.2 節の手順で求める。承認の有無は、上の「承認」で決まる (直接の呼び出しは答え済みであること、Code Mode は承認の記録に当たる項目 (4.4 節))。
    - 他 (allow か、承認のある ask だけ): 実行する。
  - 再開した worker が以後に呼ぶツールの判定も、再開を求めた要求のトークンの `groups` を使う。
- groups の変化が効く時期:
  - 中断の後に利用者が groups から外れても、変化が効くのは、変化の後に発行されたトークンで再開したときだけと見込む。変化の前に発行されたトークンは、前の `groups` を持つ。
  - この「だけ」は未確認。確かめる試験は 11 節の 3 (外す前に発行されたトークンと、外した後に発行されたトークンで再開する)。
  - 遅れは access token の寿命で決まる。値は未確認 (同じ試験で測る)。
  - 退けた案:
    - 記録したときの判定を固定する: groups から外された利用者の承認が通る。
    - 再開ごとに IdP に問い合わせる: 通信が増え、IdP の応答の契約に依存する。
- 上限:
  - 中断した要求の数には、利用者ごとの上限と、全利用者を通した上限を置く。結果だけの記録も数える。
    - 数は、記録の集合 (要求 id から記録への表) の大きさとして数える (3.3 節の「上限の数え方」)。
    - 記録を消す行では、後始末が throw しても、記録を集合から外す (finally に置く)。期限は記録の状態の一部なので、記録と一緒に無くなる。
    - 案の比較:

      | 案 | 1 人の利用者が他の利用者の枠を使えるか | 満杯のときの動作 | 上限の数 | 採否 |
      | --- | --- | --- | --- | --- |
      | 全体で 1 つ | 使える (全体の上限まで) | 新しい中断を作らず `busy_suspended` を返す | 1 | 採らない。1 人のエージェントの誤り (ask の繰り返し) が全部を埋めると、他の利用者の新しい中断も `busy_suspended` になる |
      | 利用者ごとと全体 | 利用者ごとの上限までしか使えない | 新しい中断を作らず `busy_suspended` を返す | 2 | 採る。1 人の誤りは、その人の枠で止まる。全体の上限はメモリを守る |
      | 満杯のときに最古を捨てる | 使える。新しい中断が、他の利用者の記録を捨てさせる | 最古の記録を捨てて新しい中断を作る。捨てた id は `unknown` になる | 1 | 採らない。他の利用者の承認待ちと結果が、別の利用者の要求で消える (0 節の誤った相手) |

    - どちらの上限も固定値で、値は実装で測って決める。全体の上限は、1 件あたりの資源と掛けて、プロセスのメモリに収まる値にする。1 件あたりの資源は、次の和:
      - 記録 1 件の大きさの上限 (下)
      - Code Mode 1 件の確保メモリ (7.2 節の上限のメモリ)
    - どちらかの上限に達したら、新しい中断を作らない (上の表の、記録が無いときの「中断」の行)。
  - 記録 1 件の大きさには、固定の上限を置く。値は実装で決める。
    - 大きさは、数えるものを JSON にした UTF-8 のバイト数で数える。数えるものは、状態で違う:
      - 決定の前: 元の要求の `name`・`arguments` と、承認の記録の項目 (引数を含む) の合計。項目は答え (許可) で増える。増えて上限を超えたときの扱いは未決で、実装の前に状態遷移の表に足す。
      - 決定: 結果 (元の要求は、決定に移る時の後始末で捨てている)

      Code Mode の worker は、7.2 節のメモリの上限で別に抑える。
    - 値は、7.1 節の上限 (64 KiB) に収まる `gateway__run_code` の入力を、`name` と合わせて JSON にした大きさ (エスケープで増える分を含む) を収める大きさにする。Code Mode の中断が、大きさで断られないため。
    - 7.2 節の Code Mode の結果の大きさの上限は、この上限以下の値にする。7.2 節の上限は、この節と同じもの (`gateway__run_code` の `tools/call` の結果の全体) を、同じ物差し (JSON にした UTF-8 のバイト数) で測る。そのため、7.2 節の上限に収まって終わった Code Mode の結果は、`result_too_large` にならない。
    - 直接の呼び出しの子の結果には、7.2 節の上限が掛からない。そのため、中断した呼び出しの結果を記録に入れる時にだけ、この上限を補う (次の項目)。
    - 決定に移る時に結果が上限を超えれば、そのとき結ばれた要求には結果を返し、記録は理由 `result_too_large` (6.2 節) だけを持つ。以後の再開には、`isError: true` とその理由を返す。
  - 1 つの記録の、待っているだけの要求の数には、固定の上限を置く。値は実装で決める。
    - 待っているだけの要求は、それぞれが接続と応答の待ちを持つ。モデルが `gateway__resume` を繰り返し呼んでも、増え続けないようにする。
    - 全体の数は、多くて (中断した要求の全体の上限) × (1 つの記録の上限)。接続と応答の待ちの資源は、この積で見積もる。
    - 達したときの新しい再開の扱いは、状態遷移の表の「実行中・再開」の行。
    - 上限を超えた再開に返す形の比較。上限を超えるのは、モデルが再開を繰り返したとき (0 節のエージェントの誤り)。どちらの案も待たずに返すので、モデルが再開を繰り返しても、接続と応答の待ちは増えない。物差し:
      - 記録の状態を表す旗
      - モデルの誤り
      - 実測 3 (11 節) への依存

      | 案 | 記録の状態を表す旗 | モデルの誤り | 実測 3 への依存 | 採否 |
      | --- | --- | --- | --- | --- |
      | `isError: true` と理由 `busy_waiting` | 実行が続き、後から結果を引ける状態に、終端と同じ旗を立てる | 失敗とみなすと、続いている実行を失敗として利用者に伝える | 無い | 採らない。待ちの `pending` と同じ状態を、待っているだけの要求の数で違う旗にする |
      | `pending` に `reason: "busy_waiting"` を添える | 待ちの `pending` と同じ旗 (`isError: false`) | 完了とみなすと、未完了を完了として利用者に伝える (6.2 節) | 有る。`pending` と同じく、実測 3 が済むまで実装の前提にしない (6.2 節) | 採る。実行が続き後から引ける状態を、待ちの数によらず同じ旗で表す。`gateway__resume` の待ちの `pending` も実測 3 に依るので、再開の経路を実装するのはどちらの案でも実測 3 の後になり、`isError: true` の案に実装の順の利得は無い |
- 期限:
  - 期限は、記録の状態の値の一部。状態を置き換えると、期限も一緒に置き換わる。
  - 状態ごとの期限。括弧は期限の名前で、状態遷移の表の「次の状態」の欄はこの名前で書く:
    - 待ち (新しい期限): 移った時から、下の「15 分の値」。
    - 答え済み (待ちの期限): 直前の待ちの期限を引き継ぐ。
    - 実行中 (期限なし): 持たない。実行中の時間は、次の 7.2 節の上限で抑える:
      - Code Mode: 実行の経過時間 (承認を待つ間を除く)
      - 直接の呼び出し: 子への要求 1 件の応答を待つ時間
    - 決定 (新しい期限): 移った時から、下の「15 分の値」。
  - 期限が過ぎたかは、今の状態の期限と比べて決める。前の状態の期限で起きた判定が後で走ったときも、動くのは次の両方が成り立つときだけ:
    1. 今の状態が期限を持つ。
    2. その期限が過ぎている。
  - 期限の数え方の比較:
    - 記録を作った時 (最初の中断) から数える: 承認の後の実行が長いと、実行中に期限が過ぎ、実行が `cancelled` で止まる。止まるまでに起きた子ツールの副作用は残る。採らない。
    - 待ちに入るたびと決定に移る時に新しい期限を持ち、実行中は持たない: 期限は、利用者が答える時間と結果を引く時間だけを数える。実行の時間は 7.2 節の上限が抑える。代わりに、実行中の記録は、下の 7.2 節の上限まで中断の上限の枠を占める。採る。
  - 15 分の値:
    - 15 分の固定値。
    - 値の根拠: 期限は、次の 2 つの兼ね合いで決まる:
      - 長いほど: 利用者が答えられる時間と、結果を引ける時間が延びる。
      - 短いほど: 記録が上限の枠を使う時間が縮む。

      15 分は、利用者がチャットで URL を見て、ブラウザでログインして答えるまでの見込みで、測っていない。11 節の実測 3 で、利用者が答えるまでの時間を測って見直す。
    - 設定にしない理由: 期限は上限 (固定値) と一緒に、枠が空くまでの時間を決める値で、利用者が選ぶものではない。
  - 過ぎたら、記録を消す。そのとき結ばれた要求があれば (待ちの、2025 系の元の要求。上の「状態ごとの結ばれた要求」)、`cancelled` を返す。以後の再開は、記録が無いので `unknown` になる (6.2 節)。待ち・答え済み・決定の表の「期限」の行は、これに従う。
  - 決定が新しい期限を持つ理由。比べた案:
    - 直前の待ちの期限を引き継ぐ: 実行が長いと、決定に移った時に期限が過ぎている。待ちから決定に移るときも、期限の間際なら結果を引く時間がほとんど残らない。どちらも、後の `gateway__resume` が `unknown` になって結果を失う。採らない。
    - 結果を残さない: 決まった結果を、後から来た `gateway__resume` と、同じ再送の繰り返しに返せない。採らない。
    - 新しい期限: いつ決まっても、結果を引く時間が「15 分の値」だけある。代わりに、記録が上限の枠を使う時間が延びる。採る。
- 承認を待つ間は、Code Mode の CPU の時間にも実行の経過時間 (7.2 節) にも数えない。
- 承認を待つ間の Code Mode の実行の持ち方。物差し:
  - 承認の間に保持する資源
  - 承認の前に実行した子ツールの副作用

  | 案 | 保持する資源 | 副作用 | 採否 |
  | --- | --- | --- | --- |
  | worker を止めたまま保持する | 1 件ごとに、止めた worker と QuickJS の context (入れ子の run があれば、その数だけ。7.2 節)。量は未測定 (11 節の実測 2) | 1 回だけ起きる | 採る。保持する資源は、中断の上限と期限 (上) で抑えられる |
  | 承認の後に、スクリプトを最初から実行し直す | 承認の記録だけ | 承認の前の呼び出しが、もう一度起きる | 採らない。子ツールの副作用が二重に起きる |

  1 件あたりの保持資源は、全体の上限 (上の「上限」) を決めるときに、実測 2 の値を使う。
- 同時に起きた ask: Code Mode で、worker が guest の job を回す 1 回の間に起きた ask は、1 つの操作にまとめる (上の事象「中断」)。
  - elicitation の場合: 1 回の要求に並べる。
    - 2025 系: 1 つの `elicitation/create`
    - 2026 系: 1 つの `inputRequests`
  - URL の場合: 1 つのページに並べる。
  - 答えは呼び出しごとに受ける。許可の答えは、承認の記録に呼び出しごとの項目として書く。送信の答えは、上の「受けた送信の答え」で決める。

### 6.4 ゲートウェイ自身のツール

| ツール | 役割 |

| `gateway__run_code` | Code Mode (7 節) |
| `gateway__resume` | 引数 `request_id` で、中断した要求を再開する (6.2 節) |
| (将来) `gateway__connect` | `per_user` の子に接続する。まだ接続していない子があるときだけ出す |

## 7. Code Mode

### 7.1 `gateway__run_code`

- 入力: `{ code: string }`。
  - 上限は 64 KiB (`code` を UTF-8 にしたバイト数)。超えたら、実行を始める前 (静的な検査 (7.2 節の 1) の前) に断り、`isError: true` と理由 `code_too_large` (6.2 節) を返す。入れ子の run (7.3 節) なら、その呼び出しが guest の中で `ToolError` になる。
  - async 関数の本体として書き、`return` した値が結果になる。
- 使えるもの:
  - `tools.<server>.<tool>(args): Promise<結果>`
    - 引数はそのツールの `inputSchema` に従う。
    - 戻り値は `outputSchema` があれば `structuredContent`、無ければ `{ content }`。
    - 子が `isError` を返したら、例外 (`ToolError`) にする。
  - `console.log` など: 出力を集めて、結果に入れる。
  - 言語の組み込み。例:
    - `JSON`
    - `Math`
    - `Date`
    - `Promise`
- 使えないもの:
  - ネットワーク
  - ファイル
  - env
  - 子プロセス
  - タイマー
  - `import`
  - 実行をまたいで残る記憶域
- ゲートウェイは、スクリプトを保存する機能を持たない。スクリプトを残せるのは、保存のできる子ツールを使ったときだけ。
- 結果: `structuredContent` に `{ result, logs, calls }` を入れ、`content` には、同じ値を JSON にした text を 1 つ入れる。仕様は、構造化した結果を返すツールに、後方互換のため同じ JSON を TextContent でも返すよう勧める (SHOULD。https://github.com/modelcontextprotocol/modelcontextprotocol の `docs/specification/2025-11-25/server/tools.mdx` と `docs/specification/2026-07-28/server/tools.mdx` の Structured Content、2026-10-28)。
  - `calls` には、呼んだツールと、それぞれが成功・失敗・拒否のどれだったかを入れる。
  - 失敗したときも `calls` を返す。どの副作用が起きたかを、モデルが知るため。
- description には、呼び方の規則だけを書く。個々のツールの schema は `tools/list` で読ませる。

### 7.2 実行の流れ

- 同時に動く実行の数には、利用者ごとの上限と、全利用者を通した上限を置く。
  - どちらも固定値。全体の上限は、Code Mode 1 件の確保メモリ (下の上限のメモリ) とプロセスのメモリから、実装で決める。利用者ごとの上限は、全体の上限より小さくする。
  - 数えるもの: 始まって、まだ終わっていない実行の全部。次も 1 つと数える:
    - 承認を待って止めている実行
    - 入れ子の run (7.3 節)
  - 数は、始まって終わっていない実行の集合の大きさとして数える (3.3 節の「上限の数え方」)。集合から外すのは後始末 (下) の最後。
  - どちらかに達したら、新しい実行を始めずに `busy_runs` を返す (6.2 節)。入れ子の run なら、その呼び出しが guest の中で `ToolError` になる。
  - 案の比較 (物差しは 6.3 節の「上限」の表と同じ):

    | 案 | 1 人の利用者が他の利用者の枠を使えるか | 満杯のときの動作 | 上限の数 | 採否 |
    | --- | --- | --- | --- | --- |
    | 全体で 1 つ | 使える (全体の上限まで) | 新しい実行を始めず `busy_runs` を返す | 1 | 採らない。1 人のエージェントの誤り (実行の繰り返し) が全部を埋めると、他の利用者の新しい実行も `busy_runs` になる |
    | 利用者ごとと全体 | 利用者ごとの上限までしか使えない | 新しい実行を始めず `busy_runs` を返す | 2 | 採る。1 人の誤りは、その人の枠で止まる。全体の上限はメモリを守る |
    | 満杯のときに最古を止める | 使える。新しい実行が、他の利用者の実行を止めさせる | 最古の実行を止めて新しい実行を始める | 1 | 採らない。他の利用者の実行が、別の利用者の要求で止まる (0 節の誤った相手) |

     - 6.3 節の状態遷移の表で、後始末を伴う行に当たった

     後始末の手順:
     1. guest の実行が続いていれば、interrupt handler で止める。
     2. 未解決の deferred (`newPromise` で作り、子の応答を待つもの) を dispose する。dispose は、promise と resolve・reject の 3 つの handle を解放する。dispose の後の resolve・reject は何もしないので、後から届く子の応答は guest に届かない。
     3. 実行が作った他の handle (`tools`・`console` の関数など) を dispose する。
     4. context、runtime の順に dispose する。context の dispose は、解放していない handle が残っていれば throw する。
     5. 実行の worker を終了させる (`Worker` の `terminate`)。
     6. 実行を、実行の集合 (上の「同時に動く実行の数」) から外す。

     根の実行の後始末は、次の順に行う:
     1. その入れ子の run の全部 (入れ子の入れ子を含む) を、取り消された実行として、この手順で後始末する。それぞれの worker の終了と、集合から外すことを含む。
     2. 根の実行の 1〜6 を行う。

     後始末の規則:
     - 1〜5 は入れ子の finally にする。どれかが throw しても、残りの手順を行う (例: context の dispose が throw しても、runtime を dispose する)。
     - 6 も finally に置く。
     - 全部を行った後に、最初の throw を投げ直す。
     - dispose が throw して解放できなかった heap は、5 の worker の終了で返ると見込む (未確認。11 節の実測 2)。返らなければ、次の順で行う:
       1. 実測 2 の結果を canon に足す。
       2. この後始末の順と、6.3 節の「上限」の値を書き直す。

     出典 (quickjs-emscripten 0.32.0。npm の `quickjs-emscripten` と `quickjs-emscripten-core` の tarball、2026-10-28 に確認):
     - README の Memory Management: handle は `.dispose()` で解放する。解放していない handle があると、context の dispose が throw する。
     - README の Runtime: context、runtime の順に dispose する例。
     - `quickjs-emscripten-core` の `index.d.ts` の `QuickJSDeferredPromise`: dispose は 3 つの handle を解放し、何度呼んでもよい。dispose の後の resolve・reject は何もしない。
     - 同じ `index.d.ts` の `QuickJSContext.dispose`。
4. ツール呼び出しの橋渡し: サンドボックスから来たものは、全部信頼しない入力として扱う。
   1. 引数を JSON として検証する。
   2. policy を判定する。
   3. ask なら、承認を待つ。
   4. 子へ中継する。
   5. 結果を JSON で戻す。

### 7.3 自分自身の呼び出し

- `tools.gateway.run_code({ code })` で、入れ子の実行を作る。
  - 入れ子の実行も、根の実行と同じ形で動く (worker と context は 7.2 節の 3)。型検査も policy も観測も、同じ経路を通る。
  - 根の実行と共有するもの:
    - 中断の記録と期限: 入れ子の run の ask も、根の実行の要求の中断として、同じ記録を使う。その中断で待ちに入ると、記録は新しい期限を持つ (6.3 節の「期限」)。
    - 呼び出しの予算: 7.2 節の上限のうち、ツール呼び出しの数と同時数。
  - 深さの上限は 3 の固定値。
  - 入れ子の run の ask は、その run のスクリプトの全文を付けて、新しく承認を求める。
- 使い道: 保存のできる子ツールから読んだスクリプトを、実行する。

### 7.4 進捗

クライアントが `progressToken` を付けていれば、ツール呼び出しが終わるたびに `notifications/progress` を出す。Claude Code の docs (4.2 節に挙げたもの) は、progress の通知が idle timeout を延ばすと書く (実測していない)。

## 8. 観測

### 8.1 送るもの

- trace:
  - span 名と属性は、OpenTelemetry の MCP の semantic conventions (`open-telemetry/semantic-conventions-genai` の `docs/gen-ai/mcp.md`、Development。2026-10-28) に従う。
    - span 名: `{mcp.method.name} {gen_ai.tool.name}`
    - 必須の属性: `mcp.method.name`
    - 条件つきの属性:
      - `gen_ai.tool.name`
      - `error.type` (`isError` のときは `tool_error`)
      - `jsonrpc.request.id`
    - 推奨: `mcp.protocol.version`、`gen_ai.operation.name` (`execute_tool`)
  - 規約に無いものは `sluice.*` の属性で足す:
    - `sluice.policy.decision`
    - `sluice.interaction.kind`
    - `sluice.interaction.channel`。値:
      - `form`
      - `url`
      - 結果の URL
    - `sluice.run.id`・`sluice.run.depth`・`sluice.code.sha256`・`sluice.code.bytes`
    - `user.id` (= `sub`)・`sluice.client_id`
  - span の入れ子:
    - `mcp.request`
      - 直接の呼び出し:
        - `policy.decide`
        - `interaction.wait`
        - 子への `tools/call` (CLIENT)
      - Code Mode:
        - `codemode.run`
          - `policy.decide`
          - `interaction.wait`
          - 子への `tools/call` (CLIENT)
          - 入れ子の実行 (7.3 節) の `codemode.run`
- 伝播:
  - 受け取る (次のどちらか):
    - `_meta` の `traceparent`・`tracestate`・`baggage` (SEP-414、2026-07-28 で予約)
    - HTTP ヘッダ
  - 子へ渡す: 両方に入れる。
- metrics:
  - 規約のもの: `mcp.server.operation.duration`・`mcp.client.operation.duration`
  - 足すもの:
    - 判定ごとの呼び出しの数
    - 操作の待ち時間
    - Code Mode の実行時間と、1 回あたりのツール呼び出しの数
    - 子の接続状態
- log (構造化):
  - 監査: 呼び出しごとに 1 件出す。中身:
    - 利用者
    - クライアント
    - tool
    - 判定
    - 操作の結果
    - 成否
    - 時間
    - 引数の hash と大きさ

  - 引数と結果の本文は、既定では記録しない。

## 9. 配備

- 前段の reverse proxy で TLS を終端する。
- claude.ai から使う場合:
  - ゲートウェイと authentik の両方が、インターネットから届く必要がある。
  - claude.ai の docs (`claude.com/docs/connectors/building/authentication`、2026-10-28) は、AS が `160.79.104.0/21` から届くことを求めている。
- stdio の子は、ゲートウェイのコンテナの中で子プロセスとして動く。子は信頼する前提なので、子の IO は制限しない。
- 子へ渡す値の決まりは 4.1 節。
- 秘密は次の 2 つ (将来の `per_user` で、トークンの暗号化の鍵が加わる):
  - 子の資格情報: 4.1 節の子へ渡す値。
  - cookie の署名の鍵:
    - 親の環境変数 `MCP_SLUICE_COOKIE_KEY` で渡す。名前は固定で、設定ファイルには出さない。既定の鍵は持たない。既定の鍵を持つと、渡し忘れた配備が、誰でも知る鍵で cookie を署名する。
    - 値は、32 バイト (256 bit) 以上の乱数を base64 にしたもの。作り方の例: `openssl rand -base64 32` (32 バイトの乱数を base64 の 44 文字で出す。OpenSSL 3.0.13 の Linux で測った、2026-10-28)。
    - 値の検査は、4.1 節の起動時の検査。
    - 下限の 32 バイトは、この設計が決めた値。RFC 7518 が HS256 の鍵に求める長さは未確認。実装の時に確かめて canon に足し、求める長さが 32 バイトより長ければ下限を上げる。
    - 鍵を失うか替えると、それまでに署名した cookie は署名の検査に通らず、ページはログインを求め直す。
- cookie の機構の比較。物差し:
  - 管理対象
  - 再起動・配備をまたぐ cookie の有効性
  - 無効化 (1 人のセッションを期限の前に終わらせる)
  - 保持する状態

  | 案 | 管理対象 | 再起動・配備をまたぐ有効性 | 無効化 | 保持する状態 | 採否 |
  | --- | --- | --- | --- | --- | --- |
  | 署名の鍵 (JWS) | 鍵 1 つと、その環境変数・起動時の検査 | 鍵が同じなら有効 | 1 人ずつは `exp` (4.4 節の 8 時間) まで。鍵を替えると全員 | cookie の `exp` (3.2 節) だけ | 採る。再起動と配備で、利用者がログインし直さない。1 人ずつ無効化できなくても、cookie で答えられるのは、そのログインの利用者自身の中断した要求だけ (6.2 節のページの確かめ) |
  | 不透明な id とメモリの写像 | 鍵 0 個。写像の掃除 | 再起動で写像が消え、全員がログインし直す | 即時 (写像から消す) | id からセッションへの写像 | 採らない。再起動と配備のたびに、全員がログインし直す |
  | 不透明な id と SQLite の表 | 鍵 0 個。表とその掃除と、SQLite のファイル | ファイルが残れば有効 | 即時 (行を消す) | id からセッションへの表 | 採らない。SQLite は、`per_user` (3.3 節) を足すまで持たない依存で、最初の公開に足すことになる。得るのは 1 人ずつの無効化で、その価値は署名の鍵の案の行の理由で小さい |

   - 取得が失敗すると、終わりを待っていた要求も、取り直せなかった定義として扱う。
   - 取得が失敗した後、失敗の後の間隔の間の要求は、子へ `tools/list` を送らず、取り直せなかった定義として扱う。続けて失敗すると、間隔が延びる。
   - 間隔の間に子が `list_changed` を送るか、切断して再接続すると、間隔が終わり、次の要求がすぐ取り直す。その後の失敗の間隔は、初めの値から数える。
   - 取得が成功すると間隔が終わり、その後の失敗の間隔は、初めの値から数える。
   - 取得が失敗した後に子が `list_changed` を送らなくても、間隔が過ぎた後の次の要求が定義を取り直し、成功すれば一覧に載り、クライアントへ `list_changed` が出る。
   - 子が `list_changed` を送った後の取得が失敗し、間隔が過ぎた後の取得が成功すると、クライアントへ `list_changed` が出る。
   - クライアントへの `list_changed` は、その子を使える利用者の全接続へ出る。1 つの接続への送信が失敗しても、残りの接続へ出る。
   - 寿命が過ぎた定義を取り直すと、クライアントへ `list_changed` が出る。
   - 子の 2 つが応答しないとき、1 回の `tools/list` が 2 つの子の取り直しを並行に行い、待ちが子への要求の応答を待つ上限 2 つ分にならない。
   - 取り直せなかった定義のツールの `tools/call` は、取得が子への要求の応答を待つ上限で終わったときも含めて、`child_unreachable` を返す。
3. 利用者の操作。対象:
   - 承認の届け方:
     - elicitation
     - URL
     - `gateway__resume`
   - 試験:
     - 2026 系の再送の引数だけを変えた入力で、承認が使われない (6.2 節)。
     - 「今回だけ許可」で承認した呼び出しを同じ run でもう一度呼ぶと、2 回目は承認を求め直す (6.3 節の「承認」)。
     - 記録の利用者と違う利用者か、記録のクライアントと違うクライアントが、要求 id で再開すると `unknown` を返す (6.2 節の再開の確かめ)。
     - `gateway__resume` の `request_id` に操作 id を渡すと、`request_id_is_operation_id` を返す (6.2 節)。
     - 書き換えた `requestState` の 2026 系の再送 (6.2 節の「`requestState` の署名の要否」):
       - 別の利用者の記録の要求 id に書き換えると、`unknown` を返す。
       - 待ちの操作 id と違う操作 id に書き換えた答えは、受けない (記録が変わらない)。
     - 期限 (6.3 節の「期限」):
       - 承認の後の実行が、最後に待ちに入ってから期限の値 (6.3 節の「15 分の値」) を過ぎても続く。
       - 「実行中・中断」と「実行中・完了」で記録が残る行に移ったとき、移った先の状態が、移った時からの新しい期限 (6.3 節の「期限」) を持つ。
       - 同じ 2 つの事象で、返し先の無い記録は (記録なし) に移る。
     - 期限 (`exp`) を過ぎた cookie でのページの送信を拒否する (3.2 節の JOSE のライブラリ)。
     - 「答え済み・再開」で実行を始める処理が例外を投げると、決定 (`cancelled`) に移り、その要求に `cancelled` を返す (6.3 節)。
     - 中断の後に利用者を実 authentik で groups から外し、次の 2 つのトークンで再開する (6.3 節):
       - 外す前に発行されたトークン: 外す前の `groups` で判定される。access token の寿命 (変化が効くまでの遅れ) もここで測る。
       - 外した後に発行されたトークン: 承認が使われず実行されない。
4. Code Mode:
   - 対象:
     - 型検査
     - QuickJS
     - 入れ子
   - 試験:
     - 別の run では、「この実行の間は許可」が使われない。別の run は、入れ子の run と、別の `gateway__run_code` の両方を試す (4.4 節の run id)。
     - 同じ run で「この実行の間は許可」を承認した後、公開名だけが違う ask の呼び出しは承認を求める (4.4 節の「承認の記録の項目」)。
     - 同じ run で「今回だけ許可」を承認した後、引数だけが違う同じツールの呼び出しは承認を求める (同上)。
     - 「今回だけ許可」の項目は、公開名と引数が同じで run id だけが違う呼び出し (入れ子の run) を通さない (4.4 節の「Code Mode・今回だけ許可」の鍵)。
     - `code` が入力の上限 (7.1 節) を超えると、静的な検査を始めずに `code_too_large` を返す。入れ子の run では、その呼び出しが guest の中で `ToolError` になる。
5. 観測。対象:
   - OpenTelemetry
   - compose の観測の基盤
   - ダッシュボード

最初の公開の後に、`per_user` の子 (接続、暗号化した保存) を足す。対象 (3.3 節):

- 実測: 1 の 5 を `per_user` の子で測り直す。取得の回数が利用者数に比例する (4.3 節)。
- 試験 (4.3 節):
  - 取得の最中に `list_changed` を送る子で、その取得で得た定義が古いと判定される。
  - 1 人の利用者の子との接続が切れても、他の利用者の定義は古いと判定されない。
  - 子の `list_changed` と取得の成功で出す `list_changed` は、そのトークンの利用者の接続にだけ出る。
  - 取り直しの上限 (3.3 節): 1 人の利用者の取得が利用者ごとの上限に達すると、その利用者の次の取り直しは始まらず、そのツールの `tools/call` は `busy_refetch` を返す。他の利用者の取り直しは始まる。`shared` の子の取得は、上限に数えない。
  - 利用者の取得が利用者ごとの上限に達している状態で、その 1 件が世代番号の食い違いになったら、同じ取得の中で 2 回目を送る。その定義は、2 回目が成功すれば取り直せなかった定義にならない。
  - 同じ利用者の `per_user` の子 3 つが古く、利用者ごとの上限までの残りが 2 のとき、取り直す単位は単位の鍵の辞書順の先頭 2 つで、子の設定の並びに依らない。
  - 同じ (`iss`, `sub`, server id) で子のトークンが差し替わる (id が変わる) と、前の id の定義は `tools/list` にも `tools/call` の判定にも使われず、新しい id の単位が取得から始まる。前の id の記録と世代番号は残らない。
  - 子のトークンが失効するか、利用者が子の接続を切ると、その id の記録と世代番号が無くなり、その利用者の一覧から、その子のツールが外れる。
  - 取得の途中でトークンが差し替わると、その取得の終わりは記録を置かず、`list_changed` も出さず、待っていた要求は取り直せなかった定義を受ける (4.3 節の finally の 0)。

## 12. 既存のもの

近い既存の実装と、mcp-sluice との違い:

| 名前 | 近い点 | 使わない理由 |
| --- | --- | --- |
| agentgateway | CEL の policy による RBAC と、OpenTelemetry の metrics・log・trace | README に、承認 (ask) と Code Mode の記載が無い |
| IBM mcp-context-forge | 複数の MCP サーバーを束ねる。JWT などの認証と、OpenTelemetry | README に、承認と Code Mode の記載が無い |
