# mcp-sluice 設計

mcp-sluice は、複数の子 MCP サーバーを 1 つのエンドポイントに束ねる MCP サーバー。次の機能を持つ。

- 認証: authentik (OIDC) で利用者を認証する。
- 権限: 利用者のグループとツールごとに allow/ask/deny を掛ける。
- Code Mode: TypeScript でツールを呼ぶスクリプトを実行する。
- 観測: OpenTelemetry で trace・metrics・log を送る。

この文書の読者は、mcp-sluice を実装・変更する人。この文書が仕様の正本になる。

外部依存の事実の書き方:

- 一次情報で確かめたもの: 根拠に書き、各出典に確認した日を添える。外部の契約が今も成り立つかを、後でその日から判定するため。
- 確かめられなかったもの: 「未確認」と書き、選定の根拠にしない。

一次情報は次のもの:

- 仕様の repo
- ソース
- 公式 docs

「将来」と書いた節は、最初の公開に含めない。最初の版のデータの持ち方が、それを後から足せる形になるように書いてある。

## 0. 前提

- 公開リポ (OSS) として作る。
  - 認証は OIDC の一般の仕組みで書く。設定例と手順は authentik で示す。
- 利用者は複数人。
  - authentik の application の policy を通った人が、利用者になれる。
  - 利用者ごとの権限は、トークンの `groups` で分ける。
- 対象のクライアント:
  - Claude Code
  - claude.ai (Claude Desktop と mobile を含む)
  - Codex
  - ChatGPT

  claude.ai に含まれるものは、どれも同じ callback の URL で接続する (`claude.com/docs/connectors/building/authentication` の Callback URLs、2026-10-28)。
- 守るもの:
  - エージェントの誤り。プロンプトインジェクションで書かれたスクリプトが外部へ持ち出すことも含む。
  - 誤った相手への送信。利用者 A の資格情報や承認が、利用者 B の要求に使われることも含む。
  - 平文でホストの外へ出すこと。
  - トークンの残存と流用。
- 信頼するもの:
  - ゲートウェイが動くホスト
  - 管理者が登録した子サーバー
  - authentik
  - 観測の基盤

## 1. 全体の構成

```
 MCP クライアント (Claude Code / claude.ai / Codex / ChatGPT)      ブラウザ (承認のページ)
        │ Streamable HTTP + Bearer (authentik の JWT)                    │ OIDC ログイン (同じ authentik)
        ▼                                                                  ▼
 ┌──────────────────────────── mcp-sluice (1 プロセス, Deno) ─────────────────────────────┐
 │ HTTP 層    : /mcp, /.well-known/oauth-protected-resource, /i/<id> (利用者の操作のページ) │
 │ 認証       : JWT 検証 (JWKS)、ブラウザのセッション                                     │
 │ カタログ   : 子のツールを名前空間つきで合成し、利用者ごとに policy で絞る               │
 │ Policy     : allow / ask / deny (グループつきの規則)                                    │
 │ 利用者の操作: 承認を elicitation か URL で利用者に求め、中断した要求を再開する           │
 │ Code Mode  : 型検査と変換 (typescript) → QuickJS-WASM (worker で実行)                   │
 │ 子の管理   : 子への接続、list_changed の受信                                            │
 │ 観測       : OpenTelemetry (trace / metrics / log) を OTLP で送る                         │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
        │ stdio (共有の子プロセス) / Streamable HTTP (共有の資格情報)
        ▼
 子 MCP サーバー群

 観測 (compose に同梱): Tempo (trace) / Loki (log) / Prometheus (metrics) / Grafana (UI, authentik でログイン)
```

- 実行時:
  - Deno 2.x を使う。
  - 公式 TypeScript SDK v2 (`@modelcontextprotocol/server` 2.4.0) を使う。README は、次で動くと書く (https://github.com/modelcontextprotocol/typescript-sdk の README、2026-10-28):
    - Node.js
    - Bun
    - Deno
- 持つ状態:
  - メモリだけに持つ: 中断した要求 (承認待ちの Code Mode の実行など)。
  - メモリの状態があるので、レプリカは 1 つにする。
  - 将来の `per_user` (3.3 節) で、利用者ごとの子のトークンを SQLite のファイルに暗号化して持つ。
- 配る形: コンテナイメージ。docker compose の例も付ける (ゲートウェイと観測の基盤)。

## 2. プロトコルの版

- 2 つの世代を両方受ける。
  - 2026-07-28 (最新):
    - `initialize` もセッションも無い。
    - サーバーからクライアントへの要求は、`tools/call` の結果として `input_required` を返し、クライアントが再送する形 (Multi Round-Trip Requests。以下 MRTR) だけになった。
  - 2025-11-25 まで:
    - `initialize` とセッションがある。
    - POST の SSE の流れの中で `elicitation/create` を送れる。
- 両方を受ける理由:
  - claude.ai の connector の docs が挙げる authorization の仕様は 2025-11-25 まで (https://claude.com/docs/connectors/building/index.md の Specification version、2026-10-28)。
  - Claude Code は 2026-07-28 に対応している (https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md の 2.1.281 に、2026-07-28 の接続での URL mode の elicitation がある。2026-10-28)。
- SDK v2 は 1 つの handler で両世代を受けられる (https://github.com/modelcontextprotocol/typescript-sdk の `docs/protocol-versions.md` と `examples/dual-era/README.md`、2026-10-28)。
- 2025-11-25 の経路を外せる条件: 対象のクライアント (0 節) が、どれも 2026-07-28 で接続するようになったとき。
  - 確かめ方: 11 節の実測 3。
  - 追跡先: anthropics/claude-ai-mcp#153 (claude.ai の elicitation の対応の要望)。
- 子へは、SDK v2 の client を `versionNegotiation: { mode: 'auto' }` で使う。
- `tools/list` の結果:
  - 利用者ごとに絞るので、`cacheScope: "private"` を付ける (2026-07-28 の caching)。
  - `ttlMs` は短めにし、`list_changed` を併用する。
    - クライアントへの `list_changed` は、子の定義が変わったとき (4.3 節) に出す。
    - 一覧を決める他のものが変わったとき、一覧に現れるまでの上限は `ttlMs` で決まる。他のもの:
      - 利用者の groups
      - 設定
      - 子との接続の状態

      仕様は、クライアントが結果を受けてから `ttlMs` の間、結果を新しいとみなすよう勧める。0 なら、すぐに古いとみなし、クライアントは要るたびに取り直してよい (https://github.com/modelcontextprotocol/modelcontextprotocol の `schema/2026-07-28/schema.ts` の `CacheableResult`、2026-10-28)。
    - 他のものの変化を一覧に出す方式の比較:
      - `ttlMs` を 0 にする: 古さは無くなるが、`tools/list` の回数が、クライアントが一覧を使う回数に比例する。採らない。
      - groups の変化で `list_changed` を出す: ゲートウェイが groups の変化を知るのは、次の要求のトークンを受けたときだけ (6.3 節の「groups の変化が効く時期」) で、変化の時点に出せない。採らない。
      - 短めの `ttlMs` (採る): 古さの上限は `ttlMs` で、`tools/list` の回数は `ttlMs` あたり多くて 1 回。
    - 2025 系の結果には `ttlMs` が無く、一覧を取り直す時期はクライアントが決める。
    - どちらでも、古い一覧で権限は広がらない (5.2 節の、呼び出しのたびの判定)。

## 3. 認証

### 3.1 authentik でできること・できないこと

authentik 2026.8.5 と main のソースで確認した (https://github.com/goauthentik/authentik の `authentik/providers/oauth2/` と `blueprints/system/providers-oauth2.yaml`、2026-10-28)。

機能の有無:

| 機能 | 状態 | 影響 |
| --- | --- | --- |
| Dynamic Client Registration (DCR) | 有り。ただし `goauthentik.io/oidc/dcr` scope を持つ Bearer が要る | 匿名で登録しにくる MCP クライアントは 401 で失敗する |
| Client ID Metadata Documents (CIMD) | 無し | 使えない |
| RFC 8707 `resource` | 読まない | `aud` をゲートウェイに向けられない |
| RFC 8414 のメタデータ | 有り。`/.well-known/oauth-authorization-server/application/o/<slug>/` (`urls_root.py`) が、OIDC discovery (`/application/o/<slug>/.well-known/openid-configuration`) と同じ view で返す | クライアントが作る RFC 8414 の URL が末尾の `/` まで一致して届くか、届かなければ OIDC discovery に落ちるかは未確認 (11 節の実測 1) |
| refresh token | `offline_access` のときだけ出る。既定で rotation する | claude.ai の要件 (公開クライアントの rotation) を満たす |
| 非対称の署名と JWKS | 署名鍵を設定すれば有り | 非対称の署名鍵を必ず設定する |

トークンと登録の値:

| 項目 | 既定・値 | このゲートウェイの扱い |
| --- | --- | --- |
| `aud` | provider の client_id | client_id で検証する |
| `sub` | 既定は `hashed_user_id` (authentik の設置ごとに違う) | 利用者の鍵は (`iss`, `sub`) にする |
| redirect URI | strict か regex (`fullmatch`) | loopback の任意のポートを regex で通す |
| `groups` | 既定の `profile` の scope mapping に入る。access token にも入る (`include_claims_in_id_token` の既定は true) | policy にそのまま使う |

### 3.2 方式: 事前登録した公開クライアント 1 つ

- authentik に作るもの:
  - application と OAuth2 provider を 1 組作る。
  - client type は public、署名鍵は非対称にする。
  - redirect URI (regex) を登録する。

    | クライアント | redirect URI |
    | --- | --- |
    | claude.ai | `https://claude\.ai/api/mcp/auth_callback` |
    | Claude Code | `http://(localhost\|127\.0\.0\.1):\d+/callback` |
    | Codex | 上と同じ形で、末尾に `/<id>` が付くことがある (未確認。実測で決める) |
    | mcp-sluice 自身 (ブラウザのページ) | `https://<公開ホスト>/auth/callback` |

  - scope: `openid profile email offline_access`
  - 誰が使えるかは、application に結ぶ policy で決める。
- ゲートウェイの役割 (resource server):
  - `/.well-known/oauth-protected-resource` (RFC 9728) を出す。
    - `resource` = 公開 URL
    - `authorization_servers` = [issuer]
  - 未認証には 401 と `WWW-Authenticate: Bearer resource_metadata="…"` を返す。claude.ai は 401 でしか認証を始めない (`claude.com/docs/connectors/building/authentication` の Serve discovery metadata。200 に付けた `WWW-Authenticate` は無視されると書いてある。2026-10-28)。
  - JWT は次を検証する (署名と期限の検証は JOSE のライブラリに任せる):
    - JWKS での署名
    - `iss`
    - `exp`・`nbf`
    - `aud` == 設定の client_id
- ブラウザのページ (`/i/<id>`):
  - provider は 1 つ。同じ client で authorization code + PKCE のログインをし、セッションの cookie を発行する。
- 設定は 2 つの値だけにする: `issuer` と `client_id`。authentik 以外の IdP でも同じ形で動く。
- 退けた方式: ゲートウェイ自身を OAuth の AS にし、ログインだけ IdP に任せる。
  - 退けた理由: トークンの発行・保存・失効を自前で抱えることになる。対象のクライアントは、どれも事前登録の client_id を受ける。
  - ただし、クライアントが authentik のメタデータ (RFC 8414 か OIDC discovery。3.1 節) に届かなければ、この方式が要る。メタデータを代わりに出すだけでは済まない (クライアントは `issuer` と discovery の URL の一致を検査する)。実測で決める。

### 3.3 子サーバーへの資格情報

- 受け取ったトークンを子へ流さない。MCP の仕様は token passthrough を禁止している。
- 子の資格情報は、管理者が env の名前で渡す固定のものだけ。全利用者で共有する (以下 `shared`)。種類:
  - Bearer
  - ヘッダ
  - stdio の env
- `shared` の子は誰の要求でも同じ身元で動く。誰がその子を使えるかは、policy のグループで絞る。
- 資格情報の持ち方を選ぶ設定は、将来の `per_user` を足すときに設定へ加える。

#### 将来: `per_user`

利用者ごとに、ゲートウェイが子の OAuth の client になってトークンを得る。HTTP の子だけで使える。

- 手順: 仕様の URL mode elicitation の節が定める形に従う。
  1. 利用者がまだ接続していない子のツールを呼んだら、「接続」の操作 (6 節) を作る。
  2. ページ (`/i/<id>`) で、ログインのセッションの (`iss`, `sub`) が要求の (`iss`, `sub`) と一致することを確かめる。一致すれば、子の AS へ送る。仕様は、URL を開いた人の確認を求めている。
  3. 戻ってきたトークンを、次のように保存する:
     - (`iss`, `sub`, server id) に結ぶ。
     - 保存のたびに、新しいトークンの id (128 bit の乱数) を振る。
     - 暗号化して保存する。
- 子の AS へのクライアント登録は、次の順で試す。CIMD を使う場合、ゲートウェイは自分のメタデータの文書を公開する。
  1. 事前登録
  2. CIMD
  3. DCR
- 暗号化の鍵は env で渡す。鍵を失ったら、保存したトークンは全部無効になり、利用者は再接続する。
- 子が返すツールの定義は、利用者によって違いうる。鍵は、4.4 節の表の「(将来) `per_user` の子の定義」の行に従う。
- 定義は、利用者が子に接続したときに取る。
- 定義の古さ・寿命・取り直せなかったときの扱いは、4.3 節に従う。
- 古い定義の取り直し:
  - `tools/list` と `tools/call` (`gateway__run_code` を含む) を受けたら、その要求が使う定義のうち古いものを、先に取り直す。
  - 同時に取り直す数には、利用者ごとの上限と、全利用者を通した上限を置く。
    - 案の比較は、7.2 節の同時に動く実行の上限と同じ物差しで、同じ結論になる。
    - どちらの上限も固定値で、値は実装で計測して決める。利用者ごとの上限は、全体の上限より小さくする。
    - どちらかに達していたら、取り直しを始めない。その定義は、取り直せなかった定義 (4.3 節) と同じく扱う。ただし `tools/call` の理由は `busy_refetch` (6.2 節)。
    - 数は、取り直している取得の集合の大きさとして数える。利用者ごとの数は、そのうちの利用者の分の大きさ。
  - 取り直しの枠は、取得が次のどれかで終わったときに返す:
    - 成功
    - 失敗
    - 子への要求の応答を待つ上限 (7.2 節)
    - 接続の切断
- 定義を捨てるとき:
  - 子との接続が切れた。
  - 子のトークンが失効した。
  - 子のトークンが差し替わった (トークンの id が変わる)。
  - 取ってから、定義の最長の寿命 (4.3 節) が過ぎた。
- 世代番号を採った記録。案を次の物差しで比べた:
  - 状態の数
  - 子の `list_changed` への依存
  - 取り直しの回数と経路

  | 案 | 状態の数 | 子の `list_changed` への依存 | 取り直しの回数と経路 | 採否 |
  | --- | --- | --- | --- | --- |
  | 定義ごとの印 | 定義ごとに 1 つ。`list_changed` のたびに、その接続のトークンの id の定義に印を書く | 依存する | 古い定義を使う要求のたびに、その利用者の分を 1 回。要求の経路で取り直す | 採らない。取得の最中に届いた `list_changed` の印が、その取得で得た定義に付かない |
  | `list_changed` の時点で全利用者分を取り直す | 足さない | 依存する | `list_changed` のたびに、接続している利用者の数だけ。通知の経路で、使われない定義も取り直す | 採らない |
  | 世代番号 | 子のトークンの id ごとに 1 つと、定義ごとに 1 つ。`list_changed` と接続の切断で書くのは、そのトークンの id の 1 つだけ | 依存する | 古い定義を使う要求のたびに、その利用者の分を 1 回。要求の経路で取り直す | 採る |

- 利用者に見せる一覧は、`tools/list` のたびに、その利用者の定義と接続の状態から作る。まだ接続していない利用者の一覧には、`gateway__connect` を載せる。

## 4. 子サーバーの登録と名前

### 4.1 設定ファイル

1 つの宣言的なファイル (YAML) にする。JSON Schema で検証し、変えたら再起動で反映する。

```yaml
auth:
  issuer: https://auth.example.com/application/o/mcp-sluice/
  client_id: mcp-sluice
default: ask                        # どの規則にも当たらないとき
servers:
  github:
    transport: { type: http, url: https://api.githubcopilot.com/mcp/ }
    auth: { bearer_env: GITHUB_TOKEN }   # 秘密は env の名前で参照する
    groups: [dev]                   # この子を使える人 (5.1 節)
    rules:                          # 評価の順は 5.1 節
      - { tools: "delete_*", groups: [admins], decision: ask }
      - { tools: "delete_*", groups: ["*"], decision: deny }
      - { tools: ["get_*", "list_*", "search_*"], groups: ["*"], decision: allow }
  fs:
    transport: { type: stdio, command: /usr/local/bin/fs-mcp, args: [--root, /data] }
    env: { }                        # 子へ渡す env は明示したものだけ
    groups: [dev]
    rules:
      - { tools: "write_*", groups: ["*"], decision: ask }
      - { tools: "*", groups: ["*"], decision: allow }
gateway:                            # ゲートウェイ自身のツールにも同じ規則を掛ける
  rules:
    - { tools: "*", groups: ["*"], decision: allow }
```

- 起動時の設定の検査で、次のどれかに当たれば起動を失敗させる:
  - どこかの階層に、JSON Schema に無いキーがある (`additionalProperties: false`)。綴りを誤ったキーが、黙って無視されないため。
  - 空の配列がある (`minItems: 1`)。対象:
    - server の `groups`
    - rule の `groups`
    - rule の `tools`
  - server か rule に `groups` が無い。全員に当てるなら、`groups` に `"*"` を書く (5.1 節)。
  - server id が 4.2 節の形に外れる。
  - rule の `tools` の文字列が 5.1 節の形に外れる。
  - rule の `tools` の文字列が、その server の公開名の接頭辞 `<server id>__` で始まる (5.1 節)。
  - `auth.issuer` か HTTP の子の `url` が `https:` でない。ただし、loopback の `http:` は両方に許す。平文でホストの外へ出さないため (0 節)。
    - loopback の判定: URL を parse した `hostname` が、次のどれかと等しい。文字列の前方一致で比べると、`http://localhost.example.com/` のような外のホストを通す。
      - `127.0.0.1`
      - `[::1]`
      - `localhost`
    - issuer に loopback の `http:` を許す理由: 次の 3 つを 1 つのホストに置く形 (開発や、1 人で使う配備) のため。
      - ゲートウェイ
      - authentik
      - クライアント (Claude Code など)

      issuer は、ゲートウェイが JWKS を取る先で、クライアントが認可に使う先でもある (3.2 節の `authorization_servers`)。loopback なら、どちらの通信もホストの外へ出ない。
    - 比べた案: loopback でも `https:` を要る。採らない。通信がホストの外へ出ないので、守るもの (0 節の「平文でホストの外へ出すこと」) に当たらず、開発と 1 人の配備に証明書の発行と信頼の設定を求めるだけになる。
  - `bearer_env` が指す環境変数が無い。
- stdio の `env` を省略したときは、子の環境を空にする。

### 4.2 名前

- 公開する名前は `<server>__<tool>`。
  - 区切りは `__` にする。Messages API のツール名は `^[a-zA-Z0-9_-]{1,128}$` で、`.` を含められない (`platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools`、2026-10-26)。
- server id は `^(?=.{1,16}$)[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`。
  - 公開名の区切りは最初の `__` に決まる。
  - JS の識別子として使える。
  - `gateway` は予約する。
- 合成した名前が `^[A-Za-z0-9_-]{1,64}$` に収まらないツールは公開しない。そのときは警告を log に出す。
  - 64 の根拠: OpenAI の function 名の上限。OpenAI の API の OpenAPI 定義は、Chat Completions の `FunctionObject` の `name` を「a maximum length of 64」と書く (https://github.com/openai/openai-openapi の `openapi.yaml`、2026-10-28)。Responses の `FunctionTool` の `name` には上限の記載が無い。
  - Claude Code (v2.1.292 以降) は名前の前に `mcp__<登録名>__` を足し、128 文字を超えたツールを落とす (`code.claude.com/docs/en/mcp` の「Tools with names longer than 128 characters」と、https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md の 2.1.292。2026-10-28)。
- Code Mode からは `tools.<server>.<tool>(args)` で呼ぶ。名前に `-` や `.` があれば `tools.github["create-issue"]` の形にする。

### 4.3 子の管理

- 起動時に接続する。切れたら、指数バックオフで再接続する (SDK v2 の client が再接続を持てば、それを使う)。
- `shared` の子のツールの一覧は、子への接続の中に持つ:
  - 接続したら取る。子から `list_changed` が来たら取り直す。
  - 接続が切れたら、接続と一緒に捨てる。再接続するまで、その子のツールは公開しない。
  - 取ってから、定義の最長の寿命 (下) が過ぎたら捨てる。
- ツールの定義 (`shared` の子の一覧と、3.3 節の `per_user` の子の定義) の古さは、世代番号で判定する:
  - 世代番号を持つ単位 (子への接続 1 つに 1 つ):
    - `shared` の子: server id
    - `per_user` の子: 子のトークンの id。1 人の利用者の接続・切断・`list_changed` は、他の利用者の定義を古くしない。
  - 次のときに、その単位の世代番号を 1 つ増やす:
    - その接続で、子の `list_changed` を受けた。クライアントへも、子の `list_changed` を受けた時に `list_changed` を出す。
    - その接続が切れた。
  - 接続の確立では増やさない。切断で増やした後、確立するまでは子へ要求を送れず、取得を始められない (SDK は、閉じた接続で `connect` し直すまで要求を拒否する。7.2 節の SDK の契約)。切れる前の接続で始めた取得は、切断で世代番号が変わるので、下の比較で捨てる (SDK も、切断の時に応答を待っている要求を全部拒否する。7.2 節)。
  - 定義は、子へ `tools/list` を送る前に読んだ世代番号を持つ。応答を受けたときの世代番号がそれと違えば、その定義は保持せずに取り直す。
  - 定義の持つ世代番号が今の世代番号と違えば古い。古い定義は、`tools/list` にも `tools/call` の判定にも `.d.ts` (7.2 節) にも使わない。
  - 取り直せなかった定義のツール:
    - `tools/list` に載せない。
    - `tools/call` は、`isError: true` と理由 (子に届かない) を返す。
    - 古い定義で答えない。
- 定義の最長の寿命 (`shared` の子の一覧と、`per_user` の子の定義の両方に当てる):
  - 世代番号が変わるのは、`list_changed` と切断のときだけ。子が `list_changed` を送らずに定義を変えたとき、古い定義を使う時間の上限 (古さの上限) は寿命で決まる。
  - 寿命で捨てた定義は、次にそれを使う要求で取り直す。
  - 寿命は固定値。
  - 寿命の機構の比較。どの案も、`list_changed` での取り直し (上) と併せて使う。物差し:
    - 古さの上限
    - 取得の回数
    - 取得が乗る経路

    | 案 | 古さの上限 | 取得の回数 | 取得が乗る経路 | 採否 |
    | --- | --- | --- | --- | --- |
    | 毎要求で取る | 0 (要求の時点の定義を使う) | 要求ごとに、使う子ごとに 1 回 | 全部の要求 | 採らない。取得の回数と時間が、要求の数に比例する |
    | 周期で取り直す | 周期 | 周期ごとに、定義ごとに 1 回。使われない定義も取る | 要求の外の、周期の処理 | 採らない。使われない定義も取り直し、周期の処理という管理対象が増える |
    | 接続時だけ取る | 無い (接続が続く間、変化を拾わない) | 接続ごとに 1 回 | 接続の確立 | 採らない。古さに上限が無い |
    | 寿命で捨てて次の要求で取る | 寿命 | 寿命 1 つ分の時間あたり、定義ごとに多くて 1 回。使われた定義だけ | 寿命が過ぎた後に、その定義を使う最初の要求 | 採る。古さに上限があり、使われない定義は取らない |

  - 値は、11 節の実測 5 の結果から、次の 2 つの兼ね合いで決める。寿命を短くすると、古さの上限は下がり、取得の回数は増える:
    - 取得の回数 (寿命 1 つ分の時間あたり、多くて):
      - `shared` の子: 子ごとに 1 回。
      - `per_user` の子: 子ごとに、定義を持つ利用者の数だけ (利用者数に比例する)。

      負荷は、これに取得 1 回の時間を掛けて見積もる。
    - 古さの上限: 寿命そのもの。
- stdio の子は全利用者で共有する 1 プロセスにする。利用者ごとに分けるのは範囲外。

## 5. Policy (allow / ask / deny)

### 5.1 判定

1. 利用者が server の `groups` のどれにも入っていなければ、その server のツールは全部 deny。`groups` は必須 (4.1 節の起動時の検査)。
2. server の `rules` を上から見て、次の 2 つを両方満たす最初の規則の `decision` を採る:
   - `tools` (下の形の文字列か、その配列。配列なら、どれか 1 つが当たれば当たる) が当たる。
   - `groups` に利用者が入っている (`"*"` を含む)。
3. 当たる規則が無ければ、全体の `default` (既定は ask) を採る。

- `groups` の `"*"` は全員に当たる。
- rule の `tools` の文字列:
  - 形は `^[A-Za-z0-9_*-]+$`。形に外れる記述は、起動時に拒否する (4.1 節)。
  - `*` だけを任意の文字の並び (0 文字を含む) として扱い、他の文字はそのまま比べる。
  - 照合は子の名前 (子が報告した名前。例: `create_issue`) で行う。公開名 (例: `github__create_issue`) では当たらない。公開名の接頭辞で始まる記述は、起動時に拒否する (4.1 節)。
- 上から順に評価する理由: 「admins だけ ask、他は deny」のような例外を、否定を使わずに書ける。
- 判定は `groups` と `rules` だけで行う。仕様は tool annotations (`readOnlyHint` など) を信頼しない入力として扱うよう求めている。annotations はそのままクライアントへ渡す。

### 5.2 効果

| 判定 | `tools/list` | 直接の呼び出し | Code Mode の中 |
| --- | --- | --- | --- |
| allow | 載せる | 子へ中継する | 子へ中継する |
| ask | 載せる | 承認されたら中継する。拒否・取り消し・期限切れなら `isError` で理由を返す (6.3 節) | 承認されたら中継する。拒否・取り消し・期限切れなら、実行全体を止めて `isError` で理由を返す (6.3 節) |
| deny | 載せない | 「ツールが無い」と同じエラーにする | 型定義に載せない。呼べば例外にする |

判定は、一覧を作るときと、呼び出しのたびの両方で行う。

## 6. 利用者の操作

### 6.1 操作の種類

| 種類 | 起きるとき | 利用者が見るもの |
| --- | --- | --- |
| 承認 | ask のツールが呼ばれた | server、tool、引数、呼んだクライアント。Code Mode なら run id と深さ、スクリプトの全文 |
| (将来) 接続 | `per_user` の子に、利用者のトークンが無い | 子の名前と、送られる先の AS のドメイン |

承認の選択肢:

- 今回だけ許可
- この実行の間は許可
  - Code Mode のときだけ出す。
  - 範囲は承認した run だけ (4.4 節)。
- 拒否

form で聞くときの既定の選択は「拒否」。

### 6.2 届け方

クライアントの能力ごとに、上の行から使えるものを選ぶ。

| クライアントの能力 | 承認 | (将来) 接続 |
| --- | --- | --- |
| elicitation の form と url | form で聞く | url で `/i/<id>` を開かせる |
| elicitation の form だけ | form で聞く | 結果に URL を返す (下) |
| elicitation の url だけ | 結果に URL を返す (下) | url で `/i/<id>` を開かせる |
| form も url も持たない | 結果に URL を返す (下) | 結果に URL を返す (下) |

- elicitation で聞く場合:
  - 2025 系: その場で `elicitation/create` を送って待つ。
    - 待つ時間には固定値の上限を置く。値は期限 (6.3 節) 以下で、実装で決める。上限は SDK の要求の `timeout` で渡す (7.2 節)。
    - 答えを受けたときと上限を過ぎたときの扱いは、6.3 節の状態遷移の表に従う。
  - 2026 系:
    1. `input_required` を返す。
    2. `requestState` には、要求 id・操作 id と、その署名だけを入れる。仕様は `requestState` の改ざん防止を求めている。
    3. 再送を受けたら、`requestState` の要求 id で、中断した要求の記録 (6.3 節) を引く。
    4. 再開の確かめ: 次を全部確かめる。どれかが外れれば、`isError: true` と理由 `unknown` を返す。
       - 要求 id の記録がある。
       - 呼び出しの利用者が、記録の利用者と一致する。
       - 呼び出しのクライアントが、記録のクライアントと一致する。
       - 再送のとき、`name`・`arguments` が、記録のものと等しい (4.4 節の「ツールの呼び出し」)。

       `requestState` の操作 id は、ここでは確かめない。答えを受けるかを決める照合で使う (6.3 節の「答え」)。
    5. 再送を、6.3 節の状態遷移の表の「再開」の行で扱う。答えを運ぶ再送は、先に答えの事象 (答え・欠けた答え・受けなかった答え) の行で扱う。
- 結果に URL を返す場合:
  - 要求を中断し、ツールの結果として次を返す:
    - 何が必要か (承認か接続か)
    - `/i/<操作 id>` の URL
    - 再開に使う `request_id` (要求 id。`req_` で始まる。URL の操作 id は `op_` で始まる別の値)
    - 再開の仕方
  - モデルがチャットで URL を示し、利用者はブラウザで authentik にログインして操作する。
  - そのあと、モデルが `gateway__resume({ request_id })` を呼ぶ。上の 2026 系と同じ再開の確かめを通してから、6.3 節の状態遷移の表の「再開」の行で扱う。
    - `request_id` が `op_` で始まれば、記録を引かずに `isError: true` と理由 `request_id_is_operation_id` を返す。モデルが同じ結果に並ぶ URL の操作 id を渡す誤りを、期限切れなどの `unknown` と分けて伝えるため。接頭辞だけを見るので、記録の有無は漏らさない。
  - `gateway__resume` が返すものは次のどれか。どれを返すかは 6.3 節の表で決まる:
    - 元の要求の結果
    - `pending`: `isError: false` で、次を返す。元の要求は未完了として示す。
      - `status: "pending"`
      - 再開の仕方
      - 記録が待ちなら、待っている操作の URL
    - `isError: true` と理由 (下の表)
  - `pending` は `isError: false` で返すので、クライアントのモデルが完了とみなすと、未完了の操作を完了として利用者に伝える。
    - claude.ai と Claude Code のモデルがそうしないかは未確認 (11 節の実測 3)。
    - この形は、実測 3 が済むまで `gateway__resume` の実装の前提にしない。
  - 実行中のときに `running` を返さず待つ理由:
    - 待つ時間は、期限 (6.3 節) で抑えられる。直接の呼び出しなら、子への要求の応答を待つ上限 (7.2 節) でも抑えられる。
    - 待つ要求の数は、記録ごとの上限 (6.3 節の「上限」) で抑えられる。
    - `running` を返すと、モデルが呼び直す経路と状態が 1 つ増え、`pending` と同じく、モデルが未完了を完了とみなすおそれ (上) も増える。
  - 安全性:
    - ページは、次を両方満たすときだけ答えを受ける (ページの確かめ):
      - ログインした利用者が、要求の利用者と一致する。
      - URL の操作 id が、記録が答えを待っている操作 id と一致する。
    - ページに出すものは、6.3 節の「答えを運んだものの続き」。受けた送信の結果はページに出さず、次の `gateway__resume` で返す。
    - 送信には CSRF の対策をする。
    - URL を持つだけでは何もできない。
    - モデルが URL を伝えなければ何も起きない (閉じる側に倒れる)。
- 対象のクライアント (0 節) のうち、claude.ai (Claude Desktop を含む) と ChatGPT は、「form も url も持たない」の行に当たると見込む (2026-10-27 の時点。claude.ai は anthropics/claude-ai-mcp#153 で対応が要望されている。確かめ方は 11 節の実測 3)。対応したら、上の表で form の行が自動で選ばれる。
- `isError: true` の結果に入れる理由:

  | 理由 | 返すとき |
  | --- | --- |
  | `unknown` | 再開の確かめ (上の 2026 系) のどれかが外れた (期限で消えた id を含む) |
  | `denied` | 拒否の答え (6.3 節) か、再開の直前の判定 (6.3 節) の deny で、結果が決まった |
  | `cancelled` | 6.3 節の「結果を `cancelled` にするもの」で、結果が決まった |
  | `request_id_is_operation_id` | `gateway__resume` の `request_id` が `op_` で始まる (上) |
  | `busy_suspended` | 中断した要求の数が、利用者ごとか全体の上限 (6.3 節) に達していて、新しい中断を作れない。記録は、結果だけになっても期限 (6.3 節) で消えるまで数えるので、すぐに再試行しても減らないことがある |
  | `busy_waiting` | 記録の、待っているだけの要求の数が上限 (6.3 節) に達していて、再開を待たせられない。実行は続いていて、後から再開すれば結果を引ける |
  | `busy_runs` | 同時に動く Code Mode の実行の数が、利用者ごとか全体の上限 (7.2 節) に達していて、新しい実行を始められない。実行が終われば減る |
  | `busy_refetch` | (将来) 同時に取り直す数が、利用者ごとか全体の上限 (3.3 節) に達していて、古い定義を取り直せない。取り直しが終われば減る |

- Code Mode の実行の `denied`・`cancelled` にも、7.1 節の `calls` を入れる。止めるまでに起きた副作用を、モデルが知るため。

### 6.3 中断の扱い

- 中断した要求は、メモリに記録として持つ。記録が持つもの:
  - 利用者・期限・クライアント
  - 状態 (下の状態遷移の表)。待ちは、待っている操作 id を状態の値の一部として持つ。
  - 元の `tools/call` の `name`・`arguments`。中継する server と tool は、`name` を 4.2 節の最初の `__` で分けて得る。
  - Code Mode の実行なら、Promise を待ったまま止めた worker
  - 承認の記録: 承認された呼び出しごとの項目の列。項目の種類と、それぞれの鍵・等しさ・寿命は 4.4 節の「承認の記録の項目」。
    - 承認の根拠は、記録の次のものに固定する:
      - 公開名
      - 引数
      - クライアント
      - run id (Code Mode のとき)
    - 承認で通すのは、実行する呼び出しが列の項目のどれかに当たるときだけ。当たった項目の扱いは、選択肢で分かれる:
      - 今回だけ許可: 項目を列から外してから、その呼び出しを実行する。外すことと子への中継を始めることの間に、await を挟まない。挟むと、同じ項目に当たる 2 つ目の呼び出しも通る。
      - この実行の間は許可: 外さない。
  - 結ばれた要求 (下)
  - 結果 (決まったら): 元の要求の結果、`denied`、`cancelled` のどれか。
- 結ばれた要求: 記録について、ゲートウェイがまだ応答を返していない要求。役で 2 つに分ける:
  - 実行を始めた要求: 1 つの記録に多くて 1 つ。次のどちらか:
    - 状態を「実行中」にした要求 (「答え済み・再開」の行)。
    - 2025 系の元の要求のうち、操作をその場の `elicitation/create` で聞くもの。待ちの間も結ばれたまま残る。
  - 待っているだけの要求: 実行中に来た再開で、実行の終わりか次の中断を待つもの。数には上限がある (下の「上限」)。
  - 状態ごとの結ばれた要求:

    | 状態 | 実行を始めた要求 | 待っているだけの要求 |
    | --- | --- | --- |
    | 待ち | 2025 系の元の要求だけ。他の経路の要求には、操作を届けた時に応答を返している | 無い。実行中から待ちに移る時に、全部に応答を返している |
    | 答え済み | 無い (下の「順序」) | 無い |
    | 実行中 | 多くて 1 つ。切断で外れる | 上限まで |
    | 決定 | 無い。決定に移る時に、全部に応答を返している | 無い |

  - 返し先の無い記録: 結ばれた要求が無く、要求 id をクライアントに渡していない記録。結果を引く要求も、答えを運ぶ要求も来ない。
    - 起きるのは、操作をその場の `elicitation/create` で聞く 2025 系の記録で、元の要求が切断で外れたときだけ。他の経路は、操作を届ける時に要求 id を渡す (6.2 節)。
    - 状態遷移の表は、返し先の無い記録を、中断の上限の枠を占めないように消す (「待ち・切断 (実行を始めた要求)」と、実行中の「中断」「完了」の行)。
- 答え: 操作への答えを運ぶ 1 回の送信。経路で違うのは、受ける前の確かめだけ。送信の経路:
  - 2026 系の再送
  - 2025 系の、その場の `elicitation/create` への応答
  - ページの送信
- 送信を受けるのは、次を全部満たすときだけ:
  - 経路ごとの確かめを通った:
    - 2026 系の再送: 再開の確かめ (6.2 節)。
    - ページの送信: ページの確かめ (6.2 節)。
    - 2025 系: その操作で送った `elicitation/create` への応答である (SDK が要求の id で結ぶ)。
  - 記録が待ちで、送信の操作 id が、待ちの操作 id と一致する。記録が待ちでなければ、照合する操作 id が無いので、この条件は外れる。
  - 操作の呼び出しの全部に答えがある。
- 呼び出しごとの答えの分類 (elicitation の `action` の意味を決めるのは、この表だけ):

  | 答え | 分類 |
  | --- | --- |
  | `action: "accept"` で「今回だけ許可」か「この実行の間は許可」。ページの同じ選択肢 | 許可 |
  | `action: "accept"` で「拒否」、`action: "decline"`、ページの「拒否」 | 拒否 |
  | `action: "cancel"` (利用者が選ばずに閉じた) | 取り消し |

  `action: "decline"` と `action: "cancel"` は、その elicitation に載せた呼び出しの全部への答えとする。
- 受けた送信の答えは、呼び出しごとの答えから次で決める:
  - 全部が許可: 許可。
  - 1 つでも拒否: 拒否。
  - 拒否が無く、1 つでも取り消し: 取り消し。

  拒否と取り消しのどちらでも、同じ送信の中の許可の呼び出しも実行しない。拒否を先に見るのは、利用者が明示した意思を結果の理由 (`denied`) に残すため。
- 受けなかった送信は、記録に何も書かない。外れた条件で次の 3 つに分ける。状態遷移の表の事象になるのは、初めの 2 つ:
  - 欠けた答え: 答えの無い呼び出しがあり、他の 2 つの条件は満たす。同じ操作を求め直す (下の「答えを運んだものの続き」)。仕様は、足りない入力を `input_required` で求め直すよう勧める (下の出典の `mrtr.mdx`)。
  - 受けなかった答え: 経路ごとの確かめは通り、操作 id の照合に外れた。古い操作への答えと、同じ操作への 2 回目の答えは、ここに入る。ページの送信では、ページの確かめに外れたものもここに入る (ページの確かめは操作 id の照合を含む)。
  - 2026 系の再送で、再開の確かめに外れた: `unknown` を返す (6.2 節)。
- 取り消しの形 (処理中の要求を取り消すときに、仕様が定める形。ゲートウェイが子へ伝えるときも同じ。7.2 節):
  - 2025 系: `notifications/cancelled`。
  - 2026 系:
    - Streamable HTTP: 応答の SSE の流れを閉じる。
    - stdio: `notifications/cancelled`。
- 結果を `cancelled` にするもの (これで全部):
  - 取り消しの答え (上の分類)。
  - 待ちの上限 (6.2 節)。
  - 期限 (下)。
  - 実行を始めた要求の、クライアントによる取り消し。待っているだけの要求の取り消しは、その要求が待つのをやめるだけ。
- 出典 (https://github.com/modelcontextprotocol/modelcontextprotocol の `docs/specification/`、2026-10-28 に確認):
  - elicitation の 3 つの action: `2025-11-25/client/elicitation.mdx` と `2026-07-28/client/elicitation.mdx` の Response Actions
  - 2025 系の取り消し: `2025-11-25/basic/utilities/cancellation.mdx`。`2025-11-25/basic/transports.mdx` の Streamable HTTP は、切断を取り消しと解釈すべきでないと書く。
  - 2026 系の取り消し: `2026-07-28/basic/patterns/cancellation.mdx` の Transport-Specific Cancellation。Streamable HTTP の切断を取り消しとして扱うことを求める。
  - 取り消された要求に応答しないことと、取り消しが応答の後に届きうること: 上の 2 つの `cancellation.mdx` の Behavior Requirements と Timing Considerations。
  - `2026-07-28/basic/patterns/mrtr.mdx`:
    - クライアントが再送するとは限らないこと: Server Requirements (Basic Workflow)。再送が来ない記録は、期限で消える (下の「期限」)。
    - 足りない入力を `input_required` で求め直すよう勧めること: Error Handling。
- 状態遷移の表: 中断した要求の扱いは、この表で決める。
  - 状態:

    | 状態 | 意味 |
    | --- | --- |
    | 待ち | 操作の答えを待っている。状態の値は、待っている操作 id を含む。Code Mode の worker は guest の job を回さない。子の応答は deferred に届き、guest が受けるのは実行中に戻ってから |
    | 答え済み | 許可の答えを承認の記録に書き、実行を始めていない。worker は待ちと同じく guest の job を回さない |
    | 実行中 | 再開の直前の判定を通って実行している |
    | 決定 | 結果が決まった。worker と元の要求を捨て、結果だけを持つ |

  - 事象:
    - 中断: 呼び出しの判定が ask になり、承認の記録に当たる項目が無い。
      - 直接の呼び出し: 記録を作る最初の判定でだけ起きる。
      - Code Mode: worker が guest の job を回し終えた時点で、そういう呼び出しが 1 つ以上残り、実行が完了していない。その回に起きたものを 1 つの操作にまとめる (下の「同時に起きた ask」)。完了していれば事象は「完了」で、残った呼び出しは実行しない。
    - 答え (許可)・答え (拒否)・答え (取り消し): 受けた送信 (上の「答え」)。送信の答えで 3 つに分かれる。
    - 欠けた答え・受けなかった答え: 受けなかった送信 (上)。
    - 再開: 次のどちらか。
      - 再開の確かめ (6.2 節) を通った、2026 系の再送か `gateway__resume`。
      - 答えの事象の後に、答えを運んだ要求が続けて進むこと (下の「答えを運んだものの続き」)。
    - 取り消し (実行を始めた要求)・取り消し (待っているだけの要求): その役の結ばれた要求の、クライアントによる取り消し (上の「取り消しの形」)。取り消された要求には応答しない (上の出典)。
    - 切断 (実行を始めた要求)・切断 (待っているだけの要求): 2025 系の、その役の結ばれた要求の応答の流れが切れた。答えを待っている 2025 系の元の要求も含む。2025 系の仕様は切断を取り消しと解釈すべきでないとする (上の出典) ので、取り消しとは別の事象にする。2026 系の切断は取り消しに当たる。
    - 待ちの上限: 2025 系のその場の `elicitation/create` の応答を待つ上限 (6.2 節) を過ぎた。
    - 子の待ちの上限: Code Mode の中の呼び出しで、子への要求 1 件の応答を待つ上限 (7.2 節) を過ぎた。直接の呼び出しで過ぎたときは「完了」に入る。
    - 完了: 実行が終わった。終わり方:
      - 直接の呼び出し: 子の応答を受けたか、子への要求の応答を待つ上限 (7.2 節) を過ぎた。過ぎたときの結果は、`isError: true` と理由 (子が応答しない)。
      - Code Mode: 次のどれか。
        - 正常に終わった
        - `ToolError` で終わった
        - 7.2 節の上限で止まった (子への要求の応答を待つ上限を除く)
    - 期限: 記録の期限 (下の「期限」) を過ぎた。
  - 答えを運んだものの続き: 答えの事象 (答え・欠けた答え・受けなかった答え) の行の後に、答えを運んだものがすること。

    | 答えを運んだもの | 事象 | 続き |
    | --- | --- | --- |
    | 2026 系の再送 | 答え・欠けた答え・受けなかった答え | 事象の後の状態の「再開」の行で扱う |
    | 2025 系の元の要求 | 答え・欠けた答え | 事象の後の状態の「再開」の行で扱う |
    | ページの送信 | 答え | 受け付けたことと、結果は次の `gateway__resume` で返すことを、ページに出す |
    | ページの送信 | 欠けた答え | 同じページを出し直す |
    | ページの送信 | 受けなかった答え | 「この操作は済んでいるか期限切れ」をページに出す |

    2025 系の元の要求の事象が、答えと欠けた答えだけである理由: `elicitation/create` の応答が届くのは、その操作の答えを待っている間だけ。待ちを他の事象で出る時は abort し (下の「後始末」)、abort した要求に遅れて届いた応答は、ゲートウェイの待ちに渡らない (7.2 節の SDK の契約)。
  - 待ちを知らせる形: 記録が待ちにあるか待ちに移るときに、結ばれた要求へ返すもの。

    | 要求 | 返すもの |
    | --- | --- |
    | `gateway__resume` | `pending` (6.2 節) |
    | 2026 系の再送 | 待っている操作を求める `input_required` |
    | 2025 系の元の要求 | 応答を返さず、待っている操作をその場の `elicitation/create` で聞く。要求は結ばれたまま残る |

  - 遷移。行を「状態・事象」で呼ぶ。「起きない」は、その状態ではその事象が来ないことを示す。その理由は、次のどれかを指す:
    - 結ばれた要求の表: その状態に、その役の結ばれた要求が無い (上の「状態ごとの結ばれた要求」)。
    - 状態の定義: 待ちと答え済みの間、worker は guest の job を回さない (上の「状態」)。
    - 受ける条件: 送信を受けるのは待ちだけ (上の「送信を受けるのは」)。待ちでない記録への送信は「受けなかった答え」。
    - 待ちの上限の範囲: 待ちの上限は、待ちの間に送る `elicitation/create` にだけ掛かる (上の事象「待ちの上限」)。
    - 後始末: 決定に移る時の後始末 (下) で、worker を止め、子への要求と `elicitation/create` の待ちを捨てている。

    記録が無いとき (中断で作る):

    | 事象 | 条件 | 次の状態 | すること・返すもの | 解放するもの |
    | --- | --- | --- | --- | --- |
    | 中断 | 上限 (下) に達している | (記録なし) | 記録を作らずに `busy_suspended` を返す | — |
    | 中断 | 上限に達していない | 待ち | 記録を作り、操作を届ける (6.2 節) | — |

    記録が無いときの他のもの:
    - 2026 系の再送と `gateway__resume`: 再開の確かめで外れ、`unknown` を返す (6.2 節)。
    - ページの送信: ページの確かめで外れる。「この操作は済んでいるか期限切れ」をページに出す。
    - 他の事象: 起きない。

    | 取り消し (待っているだけの要求) | — | 変えない | その要求は待つのをやめる。応答はしない。実行は続く | — |
    | 切断 (実行を始めた要求) | — | 変えない | 実行は続ける (取り消しではない)。この要求は結ばれた要求から外れる。操作をその場の `elicitation/create` で聞く記録なら、返し先の無い記録 (上) になる | — |
    | 切断 (待っているだけの要求) | — | 変えない | その要求は待つのをやめる。実行は続く | — |
    | 待ちの上限 | — | 起きない | 待ちの上限の範囲 | — |
    | 子の待ちの上限 | — | 変えない | その呼び出しが、guest の中で例外になる | その子への要求。SDK が子へ取り消しを伝える (7.2 節) |
    | 完了 | 返し先の無い記録 (上) でない | 決定 (元の要求の結果) | 結ばれた要求に結果を返す | 後始末 |
    | 完了 | 返し先の無い記録 | (記録なし) | 結果を捨てる。結果を引く要求は来ない (上の「返し先の無い記録」) | 後始末。記録を消す |
    | 期限 | — | (記録なし) | 下の「期限」 | 後始末。記録を消す |

    決定:

    | 事象 | 条件 | 次の状態 | すること・返すもの | 解放するもの |
    | --- | --- | --- | --- | --- |
    | 中断 | — | 起きない | 後始末 | — |
    | 答え (許可) | — | 起きない | 受ける条件 | — |
    | 答え (拒否) | — | 起きない | 受ける条件 | — |
    | 答え (取り消し) | — | 起きない | 受ける条件 | — |
    | 欠けた答え | — | 起きない | 受ける条件 | — |
    | 受けなかった答え | — | 変えない | 答えを運んだものの続きへ進む | — |
    | 再開 | — | 変えない | 記録の結果を返す | — |
    | 取り消し (実行を始めた要求) | — | 変えない | 何もしない。結ばれた要求の表のとおり結ばれた要求は無く、取り消しは応答の後に届きうる (上の出典) | — |
    | 取り消し (待っているだけの要求) | — | 変えない | 「決定・取り消し (実行を始めた要求)」と同じ | — |
    | 切断 (実行を始めた要求) | — | 変えない | 何もしない。結ばれた要求の表のとおり、結ばれた要求は無い | — |
    | 切断 (待っているだけの要求) | — | 変えない | 「決定・切断 (実行を始めた要求)」と同じ | — |
    | 待ちの上限 | — | 起きない | 後始末 | — |
    | 子の待ちの上限 | — | 起きない | 後始末 | — |
    | 完了 | — | 起きない | 後始末 | — |
    | 期限 | — | (記録なし) | 下の「期限」 | 記録を消す |

  - 順序:
    - 状態は、事象を受けた時に、await を挟まずに書き換える。同時に来た事象は、先に受けたものが書き換えた後の状態で扱う。例: 「答え済み」に 2 つの `gateway__resume` が同時に来たら、実行を始めるのは最初の 1 つだけで、2 つ目は「実行中・再開」の行で待つ。
    - 答えの事象と、それに続く「再開」の行は、間で await を挟まずに続けて扱う。「再開」の行が含む再開の直前の判定と、「今回だけ許可」の項目を外すことも同じ。そのため、答え済みに結ばれた要求は無い。
    - 結果を決める事象 (次の状態が「決定」か「(記録なし)」の行の事象) は先勝ち。結果が決まった後に来たものは、結果を変えない。
  - 後始末で止める・捨てるもの:
    - Code Mode の worker: 7.2 節の後始末を通して止める。
    - 子へ送って応答を待っている要求: 待ちを捨てる。SDK の要求の `signal` を abort すると、SDK が子へ取り消しを伝える (7.2 節)。遅れて届いた応答は使わない。
    - 2025 系のその場の `elicitation/create` の待ち: 同じく abort する。SDK がクライアントへ取り消しを伝える。
    - 元の要求 (`name`・`arguments`) と承認の記録。記録には結果だけを残す (「(記録なし)」に移る行では、記録ごと消す)。
- 再開の直前の判定: 「答え済み・再開」の行で、実行の直前に 5.1 節の判定をやり直す。
  - 再開は、次の経路の全部で同じに扱う。経路:
    - 2026 系の再送
    - `gateway__resume`
    - 2025 系のその場 (許可の答えを運んだ元の要求)
  - 判定する対象は、中断した要求の呼び出しの全部 (承認で止まったものも、(将来) 接続で止まったものも):
    - 直接の呼び出し: 記録の `name`
    - Code Mode: worker の中で止まっている呼び出し
  - 判定に使うのは、再開を求めた要求のトークンの `groups` (access token の claim。3.1 節)。再開を求めた要求は、上の経路のそれぞれで次のもの:
    - 2026 系の再送: その再送
    - `gateway__resume`: その呼び出し
    - 2025 系のその場: 元の要求
  - 対象の判定から、次の状態を決める:
    - どれかが deny: deny。
    - deny が無く、どれかが ask で、承認の記録に当たる項目 (4.4 節) が無い: 承認を求め直す。新しい操作 id を振り、項目の無い呼び出しだけを 6.2 節の手順で求める。
    - 他 (allow か、項目のある ask だけ): 実行する。
  - 再開した worker が以後に呼ぶツールの判定も、再開を求めた要求のトークンの `groups` を使う。
- groups の変化が効く時期:
  - 中断の後に利用者が groups から外れても、変化が効くのは、変化の後に発行されたトークンで再開したときだけと見込む。変化の前に発行されたトークンは、前の `groups` を持つ。
  - この「だけ」は未確認。確かめる試験は 11 節の 3 (外す前に発行されたトークンと、外した後に発行されたトークンで再開する)。
  - 遅れは access token の寿命で決まる。値は未確認 (同じ試験で測る)。
  - 退けた案:
    - 記録したときの判定を固定する: groups から外された利用者の承認が通る。
    - 再開ごとに IdP に問い合わせる: 通信が増え、IdP の応答の契約に依存する。
- 上限:
  - 中断した要求の数には、利用者ごとの上限と、全利用者を通した上限を置く。結果だけの記録も数える。
    - 数は、記録の集合 (要求 id から記録への表) の大きさとして数える。利用者ごとの数は、そのうちの利用者の記録の数。別の計数器を持たない。
    - 記録を消す行では、後始末が throw しても、記録を集合から外す (finally に置く)。
    - 案の比較:

      | 案 | 1 人の利用者が他の利用者の枠を使えるか | 満杯のときの動作 | 上限の数 | 採否 |
      | --- | --- | --- | --- | --- |
      | 全体で 1 つ | 使える (全体の上限まで) | 新しい中断を作らず `busy_suspended` を返す | 1 | 採らない。1 人のエージェントの誤り (ask の繰り返し) が全部を埋めると、他の利用者の新しい中断も `busy_suspended` になる |
      | 利用者ごとと全体 | 利用者ごとの上限までしか使えない | 新しい中断を作らず `busy_suspended` を返す | 2 | 採る。1 人の誤りは、その人の枠で止まる。全体の上限はメモリを守る |
      | 満杯のときに最古を捨てる | 使える。新しい中断が、他の利用者の記録を捨てさせる | 最古の記録を捨てて新しい中断を作る。捨てた id は `unknown` になる | 1 | 採らない。他の利用者の承認待ちと結果が、別の利用者の要求で消える (0 節の誤った相手) |

    - どちらの上限も固定値で、値は実装で測って決める。全体の上限は、Code Mode 1 件の確保メモリ (7.2 節の上限のメモリ) と掛けて、プロセスのメモリに収まる値にする。
    - どちらかの上限に達したら、新しい中断を作らない (上の表の、記録が無いときの「中断」の行)。
  - 1 つの記録の、待っているだけの要求の数には、固定の上限を置く。値は実装で決める。
    - 待っているだけの要求は、それぞれが接続と応答の待ちを持つ。モデルが `gateway__resume` を繰り返し呼んでも、増え続けないようにする。
    - 全体の数は、多くて (中断した要求の全体の上限) × (1 つの記録の上限)。接続と応答の待ちの資源は、この積で見積もる。
    - 達したら、新しい再開は、`gateway__resume` と 2026 系の再送の両方で、待たずに `isError: true` と理由 `busy_waiting` (6.2 節) を返す (「実行中・再開」の行)。
    - `pending` と比べた: 上限を超えるのは、モデルが再開を繰り返したとき (0 節のエージェントの誤り)。`pending` (`isError: false`) は同じ呼び直しを促し、2026 系の再送には形が無く、実測 3 の前は前提にしない (6.2 節)。`busy_waiting` は、モデルが失敗とみなす誤りが起きうるが、理由が後からの再開で結果を引けることを示す (6.2 節の表)。
- 期限:
  - 記録を作った時 (最初の中断) から 15 分の固定値。
    - 値の根拠: 期限は 2 つを兼ねる。長いほど、利用者が答えられる時間と結果を引ける時間が延び、短いほど、記録が上限の枠を使う時間が縮む。15 分は、利用者がチャットで URL を見て、ブラウザでログインして答えるまでの見込みで、測っていない。11 節の実測 3 で、利用者が答えるまでの時間を測って見直す。
    - 設定にしない理由: 期限は上限 (固定値) と一緒に、枠が空くまでの時間を決める値で、利用者が選ぶものではない。
  - 過ぎたら、記録を消す。そのとき結ばれた要求があれば (待ちと実行中。上の「状態ごとの結ばれた要求」)、`cancelled` を返す。以後の再開は、記録が無いので `unknown` になる (6.2 節)。各状態の表の「期限」の行は、これに従う。
  - 結果が決まったら (「決定」に移ったら)、期限を結果が決まった時から 15 分に置き直す。比べた案:
    - 元の期限のまま: 期限の間際に結果が決まると、結果を引く時間がほとんど残らず、後の `gateway__resume` が `unknown` になって結果を失う。採らない。
    - 結果を残さない: 決まった結果を、後から来た `gateway__resume` と、同じ再送の繰り返しに返せない。採らない。
    - 置き直す: いつ決まっても、結果を引く時間が 15 分ある。代わりに、記録が上限の枠を使う時間が延びる。採る。
- 承認を待つ間は、Code Mode の CPU の時間に数えない。
- 承認を待つ間の Code Mode の実行の持ち方。物差し:
  - 承認の間に保持する資源
  - 承認の前に実行した子ツールの副作用

  | 案 | 保持する資源 | 副作用 | 採否 |
  | --- | --- | --- | --- |
  | worker を止めたまま保持する | 1 件ごとに、止めた worker と QuickJS の context。量は未測定 (11 節の実測 2) | 1 回だけ起きる | 採る。保持する資源は、中断の上限と期限 (上) で抑えられる |
  | 承認の後に、スクリプトを最初から実行し直す | 承認の記録だけ | 承認の前の呼び出しが、もう一度起きる | 採らない。子ツールの副作用が二重に起きる |

  1 件あたりの保持資源は、全体の上限 (上の「上限」) を決めるときに、実測 2 の値を使う。
- 同時に起きた ask: Code Mode で、worker が guest の job を回す 1 回の間に起きた ask は、1 つの操作にまとめる (上の事象「中断」)。
  - elicitation の場合: 1 回の要求に並べる。
    - 2025 系: 1 つの `elicitation/create`
    - 2026 系: 1 つの `inputRequests`
  - URL の場合: 1 つのページに並べる。
  - 答えは呼び出しごとに受ける。許可の答えは、承認の記録に呼び出しごとの項目として書く。送信の答えは、上の「受けた送信の答え」で決める。

## 7. Code Mode

### 7.1 `gateway__run_code`

- 入力: `{ code: string }`。上限は 64 KiB。
  - async 関数の本体として書き、`return` した値が結果になる。
- 使えるもの:
  - `tools.<server>.<tool>(args): Promise<結果>`
    - 引数はそのツールの `inputSchema` に従う。
    - 戻り値は `outputSchema` があれば `structuredContent`、無ければ `{ content }`。
    - 子が `isError` を返したら、例外 (`ToolError`) にする。
  - `console.log` など: 出力を集めて、結果に入れる。
  - 言語の組み込み。例:
    - `JSON`
    - `Math`
    - `Date`
    - `Promise`
- 使えないもの:
  - ネットワーク
  - ファイル
  - env
  - 子プロセス
  - タイマー
  - `import`
  - 実行をまたいで残る記憶域
- ゲートウェイは、スクリプトを保存する機能を持たない。スクリプトを残せるのは、保存のできる子ツールを使ったときだけ。
- 結果: `structuredContent` に `{ result, logs, calls }` を入れる。
  - `calls` には、呼んだツールと、それぞれが成功・失敗・拒否のどれだったかを入れる。
  - 失敗したときも `calls` を返す。どの副作用が起きたかを、モデルが知るため。
- description には、呼び方の規則だけを書く。個々のツールの schema は `tools/list` で読ませる。

### 7.2 実行の流れ

- 同時に動く実行の数には、利用者ごとの上限と、全利用者を通した上限を置く。
  - どちらも固定値。全体の上限は、Code Mode 1 件の確保メモリ (下の上限のメモリ) とプロセスのメモリから、実装で決める。利用者ごとの上限は、全体の上限より小さくする。
  - 数えるもの: 始まって、まだ終わっていない実行の全部。次も 1 つと数える:
    - 承認を待って止めている実行
    - 入れ子の run (7.3 節)
  - 数は、始まって終わっていない実行の集合の大きさとして数える。利用者ごとの数は、そのうちの利用者の実行の数。別の計数器を持たない。集合から外すのは後始末 (下) の最後。
  - どちらかに達したら、新しい実行を始めずに `busy_runs` を返す (6.2 節)。入れ子の run なら、その呼び出しが guest の中で `ToolError` になる。
  - 案の比較 (物差しは 6.3 節の「上限」の表と同じ):

    | 案 | 1 人の利用者が他の利用者の枠を使えるか | 満杯のときの動作 | 上限の数 | 採否 |
    | --- | --- | --- | --- | --- |
    | 全体で 1 つ | 使える (全体の上限まで) | 新しい実行を始めず `busy_runs` を返す | 1 | 採らない。1 人のエージェントの誤り (実行の繰り返し) が全部を埋めると、他の利用者の新しい実行も `busy_runs` になる |
    | 利用者ごとと全体 | 利用者ごとの上限までしか使えない | 新しい実行を始めず `busy_runs` を返す | 2 | 採る。1 人の誤りは、その人の枠で止まる。全体の上限はメモリを守る |
    | 満杯のときに最古を止める | 使える。新しい実行が、他の利用者の実行を止めさせる | 最古の実行を止めて新しい実行を始める | 1 | 採らない。他の利用者の実行が、別の利用者の要求で止まる (0 節の誤った相手) |


1. 静的な検査: typescript 6.x の API を、プロセスの中で仮想のファイルシステムを使って呼ぶ。
   - `import`・`export`・`require` があれば拒否する。
   - 利用者から見えるツール (deny を除く) の `.d.ts` を、JSON Schema から生成して型検査する。型エラーがあれば実行せずに返す (副作用の前に、引数の誤りを直させる)。
     - `.d.ts` は、各実行のためだけに、その時点の次のものから作る:
       - 一覧: 利用者から見えるツールの、古くない定義 (4.3 節)
       - policy: 利用者の groups と設定
     - 一覧 (`list_changed`) と利用者の groups は、実行の間に変わりうる。
     - 作り方の比較:

       | 案 | 生成の回数 | 1 回あたりの時間 | 鍵の正しさ | 保持の寿命 |
       | --- | --- | --- | --- | --- |
       | 実行ごとに作る (採る) | 実行ごとに 1 回 | 未測定 (11 節の実測 4) | 鍵を持たない | その実行の間だけ |
       | 鍵で保持する | 鍵が変わったときだけ | 未測定 (11 節の実測 4) | 鍵は、`.d.ts` を決めるものを全部含む必要がある (下)。1 つ漏れれば、古い `.d.ts` で型検査する | 鍵が変わるか、捨てる時期を別に決めるまで |

     - 「鍵で保持する」の鍵に要る入力:
       - policy: 上の `.d.ts` の入力と同じ
       - 見えるツールの集合: 接続していて、古くない定義を持つ子の集合。古くない定義は、定義の世代番号が今の世代番号と同じで、取ってから最長の寿命 (4.3 節) が過ぎていないもの
       - 定義の値: 見えるツールの定義を取るたびに振る値
     - 定義の世代番号 (4.3 節) と `per_user` の子のトークンの id では足りない。どちらも、寿命で取り直した定義の中身の変化と、取り直せなかった定義が取り直せたことでは変わらない (4.3 節)。
     - 定義を取るたびに振る値だけでも足りない。次は、定義を取らずに集合の構成を変える:
       - 子の切断
       - 取得の失敗
       - 世代番号の更新 (`list_changed`)
       - 寿命切れ
     - 実行ごとに作る形を採る。見直す条件: 11 節の実測 4 で、1 回の時間が実行全体に占める割合が閾値を超えたら、鍵で保持する形に替える。
       - 閾値は実測 4 の後に決める。
       - 前もって決めない理由: 比べる相手の実行全体の時間は、子ツールの応答の時間で決まり、子ごとに桁が違いうる。実測の前には、割合のどのあたりで生成の時間が利用者の待ちに効くかの見当がつかない。
   - typescript は 6.x に固定する。7.0.2 (2026-10-28 の npm の dist-tag latest) の package は `transpileModule` を持たない。`.` の export は版の文字列だけで、他の export は `./unstable/*` だけ (npm の typescript@7.0.2 の tarball、2026-10-28 に確認。canon: facts/typescript/v7-package-lacks-transpile-module)。外せる条件: 7.x の API が、仮想のファイルシステムでの型検査と JS への変換を提供したとき。
2. TS を JS に変換する (同じ compiler で)。
3. 実行: QuickJS-WASM (quickjs-emscripten) で、実行ごとに新しい context を作り、worker thread で回す。
   - 実行の基盤の比較。物差し:
     - 何もしないときに IO を持つか
     - 閉じるのに要る手当て
     - 依存の状態

     | 候補 | 何もしないときの IO | 閉じるのに要る手当て | 依存の状態 | 採否 |
     | --- | --- | --- | --- | --- |
     | QuickJS-WASM (quickjs-emscripten) | 無い (下の実測)。README は「By default, no host functionality is exposed to code running inside QuickJS」と書く | 無し。渡すのは `tools` と `console` だけ | 版は 1.0 未満。README は「has not been audited」と書く | 採る。IO が無く、手当ても要らない。依存の状態には難がある |
     | Deno の子プロセス (許可フラグ無し) | 有る (下の実測の 3 つ) | `--no-remote`・`--no-npm`・実行ごとの `DENO_DIR`・スクリプトを文字列で評価すること | Deno は実行時 (1 節) で、足す依存は無い | 採らない。IO が有り、閉じるのに手当てが要る |
     | Deno の Worker (`deno.permissions: "none"`) | 有る (下の実測の 2 つ目と 3 つ目) | 上と同じ | `deno.permissions` は unstable の API で、`--unstable-worker-options` が要る | 採らない。IO が有り、閉じるのに手当てが要る。unstable の API に依る |
     | isolated-vm | 無い | 別のプロセスに置くこと。README は、V8 は普通の JS で落とされうるので、重要な基盤とは別の node のプロセスに置くよう勧める | README は maintenance mode と書く | 採らない。IO は無いが、別のプロセスが要る。依存の状態には難がある |
     | Cloudflare の Dynamic Worker (`@cloudflare/codemode` が使う形) | `globalOutbound: null` で外へ出ない | Workers の `worker_loaders` の binding が要る | `@cloudflare/codemode` の README は Experimental と書く | 採らない。自前のホストで動かす前提に合わない |

     依存の状態は、QuickJS (1.0 未満・未監査) と isolated-vm (maintenance mode) の両方に難がある。IO と手当てで QuickJS を採る。依存の状態から残るリスクには、実行の基盤を 1 つの interface の裏に置き、差し替えをその裏だけで済ませることで備える。

     実測 (deno 2.9.8、Linux。手順と結果は canon):
     - Deno の子プロセス (許可フラグ無し) に、次の IO がある (canon: facts/deno/io-without-permission-flags):
       - `localStorage` が実行をまたいで残る。
       - 文字列リテラルの `import("file:///…")` が、読み取りの許可なしに通る。
       - `npm:` のモジュールが、ネットワークの許可なしに取れる。
     - `deno.permissions: "none"` の Worker では、2 つ目と 3 つ目が同じく通り、`localStorage` は定義されない (同じ canon)。
     - QuickJS-WASM (quickjs-emscripten 0.32.0) で、新しい context に同じ試験を回すと、どれも通らない (canon: facts/quickjs-emscripten/no-host-io-by-default):
       - 文字列リテラルの `import("file:///…")` と `import("npm:…")` は、モジュールを読めずに失敗する。
       - 次は定義されない:
         - `localStorage` などの記憶域
         - fs の API (`Deno`・`require` など)
         - `fetch`
       - 前の context の `globalThis` への書き込みは、新しい context に残らない。
     - 測っていないもの:
       - worker の中の QuickJS。上の QuickJS の試験は main thread の context で測った。11 節の実測 2 で測る。
       - Deno の子プロセスと Worker の手当て (`--no-remote`・`--no-npm` など) の効き。

     - Deno の Worker:

   - 非同期の橋渡しは、`newPromise` と `executePendingJobs` で行う (`Promise.all` で並行に呼べる)。
   - 上限は固定値で、値は実装で計測して決める:
     - メモリ
     - スタック
     - CPU の時間 (worker が JS を回した時間)

   - SDK の契約のうち、型定義に書かれているもの (npm の `@modelcontextprotocol/client` と `@modelcontextprotocol/server` の 2.4.0 の tarball の `dist/*.d.mts`、2026-10-28 に確認)。公開の member:
     - `RequestOptions` の `timeout`: 過ぎると、`request()` が `SdkErrorCode.RequestTimeout` で拒否する。渡さなければ `DEFAULT_REQUEST_TIMEOUT_MSEC` (60000 ミリ秒) を使う。
     - `RequestOptions` の `signal`: 処理中の要求の取り消しに使う。
     - `Transport` の `hasPerRequestStream`: 2026-07-28 の接続で、これが真の transport (Streamable HTTP) では、protocol 層は取り消しを 6.3 節の「取り消しの形」の Streamable HTTP の形で伝える。
     - サーバーからクライアントへの要求 (2025 系のその場の `elicitation/create`。6.2 節) は、server の `elicitInput` で送り、同じ `RequestOptions` を受ける。
       - 2.4.0 の型定義で `@deprecated`。doc は、2026-07-28 の要求では throw し、代わりに handler から `inputRequired(...)` を返すよう書く。撤去の時期は書かれていない。
       - SDK の版を上げるたびに、`elicitInput` が残っているかを確かめる。消えたら、2025 系の接続へは、操作を 6.2 節の「結果に URL を返す」形で届ける (2025 系に `input_required` は無い。2 節)。

     protected の member (subclass 向けの hook。この設計は `Protocol` を subclass しないので、hook の doc が書く base の処理の結果だけに依る):
     - `Protocol` の `_onclose`: doc は、subclass が override したら `super._onclose()` を呼ぶよう求め、base の処理を書く。base の処理は、transport が閉じたときに、応答を待っている要求を決着させ、`timeout` の計時を止め、処理中の要求を abort する。
   - SDK の契約のうち、型定義に書かれておらず、実装で確かめたもの (同じ tarball の `dist/*.mjs` の `Protocol`。source map が指すソースは `core-internal/src/shared/protocol.ts`。2026-10-28 に確認):
     - `timeout` を過ぎるか `signal` が abort されると、待ちを拒否し、相手へ取り消しを伝える。形は 6.3 節の「取り消しの形」で、上の `hasPerRequestStream` で選ぶ。型定義の `timeout` と `signal` は、`request()` の拒否だけを書く。
     - 閉じたときの拒否は `SdkErrorCode.ConnectionClosed`。閉じた後、`connect` し直すまでの `request()` は `Not connected` で拒否する。
     - 拒否した後に届いた応答は、待ちに渡さず `onerror` に送る。
     - 外せる条件: 型定義か SDK の docs がこれらを書いたら、そちらを出典にする。それまでは、SDK の版を上げるたびに、11 節の実測 6 で確かめ直す。
   - 実行の終わりは、どれも 1 つの後始末を通す。実行の終わり:
     - 正常に終わった
     - `ToolError` で終わった
     - 上の上限で止まった (子への要求 1 件の応答を待つ時間は除く。その呼び出しの例外になる)
     - 6.3 節の状態遷移の表で、後始末を伴う行に当たった

     後始末の手順:
     1. guest の実行が続いていれば、interrupt handler で止める。
     2. 未解決の deferred (`newPromise` で作り、子の応答を待つもの) を dispose する。dispose は、promise と resolve・reject の 3 つの handle を解放する。dispose の後の resolve・reject は何もしないので、後から届く子の応答は guest に届かない。
     3. 実行が作った他の handle (`tools`・`console` の関数など) を dispose する。
     4. context、runtime の順に dispose する。context の dispose は、解放していない handle が残っていれば throw する。
     5. 実行を、実行の集合 (上の「同時に動く実行の数」) から外す。1〜4 のどれかが throw しても外す (finally に置く)。

     出典 (quickjs-emscripten 0.32.0。npm の `quickjs-emscripten` と `quickjs-emscripten-core` の tarball、2026-10-28 に確認):
     - README の Memory Management: handle は `.dispose()` で解放する。解放していない handle があると、context の dispose が throw する。
     - README の Runtime: context、runtime の順に dispose する例。
     - `quickjs-emscripten-core` の `index.d.ts` の `QuickJSDeferredPromise`: dispose は 3 つの handle を解放し、何度呼んでもよい。dispose の後の resolve・reject は何もしない。
     - 同じ `index.d.ts` の `QuickJSContext.dispose`。
4. ツール呼び出しの橋渡し: サンドボックスから来たものは、全部信頼しない入力として扱う。
   1. 引数を JSON として検証する。
   2. policy を判定する。
   3. ask なら、承認を待つ。
   4. 子へ中継する。
   5. 結果を JSON で戻す。

### 7.3 自分自身の呼び出し

- `tools.gateway.run_code({ code })` で、入れ子の実行を作る。
  - 入れ子の実行は新しい context で動く。型検査も policy も観測も、同じ経路を通る。
  - 根の実行と共有するもの:
    - 期限: 6.3 節の中断の期限。入れ子の run の ask も、根の実行の要求の中断として、同じ記録と期限を使う。
    - 呼び出しの予算: 7.2 節の上限のうち、ツール呼び出しの数と同時数。
  - 深さの上限は 3 の固定値。
  - 入れ子の run の ask は、その run のスクリプトの全文を付けて、新しく承認を求める。
- 使い道: 保存のできる子ツールから読んだスクリプトを、実行する。

### 7.4 進捗

クライアントが `progressToken` を付けていれば、ツール呼び出しが終わるたびに `notifications/progress` を出す。Claude Code の docs (4.2 節に挙げたもの) は、progress の通知が idle timeout を延ばすと書く (実測していない)。

## 8. 観測

### 8.1 送るもの

- trace:
  - span 名と属性は、OpenTelemetry の MCP の semantic conventions (`open-telemetry/semantic-conventions-genai` の `docs/gen-ai/mcp.md`、Development。2026-10-28) に従う。
    - span 名: `{mcp.method.name} {gen_ai.tool.name}`
    - 必須の属性: `mcp.method.name`
    - 条件つきの属性:
      - `gen_ai.tool.name`
      - `error.type` (`isError` のときは `tool_error`)
      - `jsonrpc.request.id`
    - 推奨: `mcp.protocol.version`、`gen_ai.operation.name` (`execute_tool`)
  - 規約に無いものは `sluice.*` の属性で足す:
    - `sluice.policy.decision`
    - `sluice.interaction.kind`
    - `sluice.interaction.channel`。値:
      - `form`
      - `url`
      - 結果の URL
    - `sluice.run.id`・`sluice.run.depth`・`sluice.code.sha256`・`sluice.code.bytes`
    - `user.id` (= `sub`)・`sluice.client_id`
  - span の入れ子:
    - `mcp.request`
      - 直接の呼び出し:
        - `policy.decide`
        - `interaction.wait`
        - 子への `tools/call` (CLIENT)
      - Code Mode:
        - `codemode.run`
          - `policy.decide`
          - `interaction.wait`
          - 子への `tools/call` (CLIENT)
          - 入れ子の実行 (7.3 節) の `codemode.run`
- 伝播:
  - 受け取る (次のどちらか):
    - `_meta` の `traceparent`・`tracestate`・`baggage` (SEP-414、2026-07-28 で予約)
    - HTTP ヘッダ
  - 子へ渡す: 両方に入れる。
- metrics:
  - 規約のもの: `mcp.server.operation.duration`・`mcp.client.operation.duration`
  - 足すもの:
    - 判定ごとの呼び出しの数
    - 操作の待ち時間
    - Code Mode の実行時間と、1 回あたりのツール呼び出しの数
    - 子の接続状態
- log (構造化):
  - 監査: 呼び出しごとに 1 件出す。中身:
    - 利用者
    - クライアント
    - tool
    - 判定
    - 操作の結果
    - 成否
    - 時間
    - 引数の hash と大きさ
  - Code Mode のソース: 実行ごとに全文を 1 件出し、`trace_id`・`span_id` で trace とつなぐ。
    - span の属性に入れない理由: Tempo は 2048 バイトを超える属性を既定で切り詰め (`max_attribute_bytes`)、上限を上げると querier が out-of-memory になりうると docs が警告している (grafana/tempo の `docs/sources/tempo/configuration/_index.md`、2026-10-27)。
    - Loki の 1 行の上限が 64 KiB の入力を受けられるかは、未確認 (実装の前に確かめる)。
  - 引数と結果の本文は、既定では記録しない。

### 8.2 基盤と UI

compose に、Grafana・Tempo・Loki・Prometheus を同梱する。

比べる物差し:

- 可動部品の数: 次の機能をそろえるのに要るコンテナの数。
  - trace
  - log
  - metrics
  - UI のログイン
- 依存する契約の安定性: ゲートウェイが送る OTLP の受け口と、UI のログインについて、一次情報が書く状態。

| 候補 | コンテナの数 | 依存する契約の安定性 | 扱い |
| --- | --- | --- | --- |
| **Grafana + Tempo + Loki + Prometheus** | 4 | Tempo の README は OpenTelemetry 互換と書く。Loki の docs は `/otlp` で OpenTelemetry の log を native に受けると書く。Prometheus は通常のフラグ `--web.enable-otlp-receiver` で受ける。UI のログインは、Grafana の generic OAuth の docs が書く | 選ぶ。確かめた事実は表の下 |
| grafana/otel-lgtm | 1 | README が、開発・デモ・テスト用と書く | 退ける。コンテナの数では 4 対 1 で負けるが、README が書く用途 (開発・デモ・テスト) が運用に合わないので採らない |

      - 非同期の橋渡し
      - interrupt
      - メモリの上限
      - worker の中で、7.2 節 3 の IO の試験が通らないこと
      - 承認を待って止めた worker 1 件が保持するメモリ (6.3 節の「承認を待つ間の Code Mode の実行の持ち方」)
   3. elicitation:
      - Claude Code で 2025 系と 2026 系。
      - claude.ai で、結果に URL を返す経路。
      - Claude Desktop と ChatGPT が、elicitation の form と url に対応するか (6.2 節の表のどの行に当たるか)。
      - claude.ai と Claude Code のモデルが、`gateway__resume` の `pending` (`isError: false`。6.2 節) を、利用者に未完了として伝えるか。崩れれば、未完了の操作を完了として利用者に伝える。
      - 利用者が操作を受けてから答えるまでの時間 (6.3 節の期限の値の根拠)。
   4. Code Mode の静的な検査 (7.2 節) で、`.d.ts` の生成と型検査にかかる時間。
   5. 定義の最長の寿命 (4.3 節) を決める値。対象は `shared` の子 (`per_user` の子は、足すときに測り直す)。測るもの:
      - 子ごとの、取得 (`tools/list`) 1 回の時間
      - 子が `list_changed` を送らずに定義を変える頻度
   6. SDK の取り消しと時限の経路 (7.2 節の、実装で確かめた SDK の契約)。2025 系と 2026 系の接続で、stdio と Streamable HTTP のそれぞれに 1 回ずつ実際に回す。結果は、実装の前に canon に出典つきで足す。確かめること:
      - 時限 (`timeout`) を過ぎた要求と、`signal` を abort した要求で、相手へ 6.3 節の「取り消しの形」で取り消しが伝わる。
      - 閉じた後、`connect` し直すまでの `request()` が拒否される。
      - 拒否の後に届いた応答が、待ちに渡らない。
2. 中継と allow/deny と認証 (MVP)。試験 (`shared` の子。4.3 節):
   - 取得の最中に子が切断されると、その取得で得た定義が古いと判定される。
   - 取得の最中に子が `list_changed` を送ると、その取得で得た定義が古いと判定される。
   - 最長の寿命が過ぎた定義は、次にそれを使う要求で取り直される。
   - 接続の確立では、世代番号が変わらない。
3. 利用者の操作。対象:
   - 承認の届け方:
     - elicitation
     - URL
     - `gateway__resume`
   - 試験:
     - 2026 系の再送の引数だけを変えた入力で、承認が使われない (6.2 節)。
     - 「今回だけ許可」で承認した呼び出しを同じ run でもう一度呼ぶと、2 回目は承認を求め直す (6.3 節の「承認の記録」)。
     - 記録の利用者と違う利用者か、記録のクライアントと違うクライアントが、要求 id で再開すると `unknown` を返す (6.2 節の再開の確かめ)。
     - `gateway__resume` の `request_id` に操作 id を渡すと、`request_id_is_operation_id` を返す (6.2 節)。
     - 中断の後に利用者を実 authentik で groups から外し、次の 2 つのトークンで再開する (6.3 節):
       - 外す前に発行されたトークン: 外す前の `groups` で判定される。access token の寿命 (変化が効くまでの遅れ) もここで測る。
       - 外した後に発行されたトークン: 承認が使われず実行されない。
4. Code Mode:
   - 対象:
     - 型検査
     - QuickJS
     - 入れ子
   - 試験:
     - 別の run では、「この実行の間は許可」が使われない。別の run は、入れ子の run と、別の `gateway__run_code` の両方を試す (4.4 節の run id)。
     - 同じ run で「この実行の間は許可」を承認した後、公開名だけが違う ask の呼び出しは承認を求める (4.4 節の「承認の記録の項目」)。
     - 同じ run で「今回だけ許可」を承認した後、引数だけが違う同じツールの呼び出しは承認を求める (同上)。
5. 観測。対象:
   - OpenTelemetry
   - compose の観測の基盤
   - ダッシュボード

最初の公開の後に、`per_user` の子 (接続、暗号化した保存) を足す。対象 (3.3 節):

- 実測: 1 の 5 を `per_user` の子で測り直す。取得の回数が利用者数に比例する (4.3 節)。
- 試験 (4.3 節):
  - 取得の最中に `list_changed` を送る子で、その取得で得た定義が古いと判定される。
  - 1 人の利用者の子との接続が切れても、他の利用者の定義は古いと判定されない。

## 12. 既存のもの

近い既存の実装と、mcp-sluice との違い:

| 名前 | 近い点 | 使わない理由 |
| --- | --- | --- |
| agentgateway | CEL の policy による RBAC と、OpenTelemetry の metrics・log・trace | README に、承認 (ask) と Code Mode の記載が無い |
| IBM mcp-context-forge | 複数の MCP サーバーを束ねる。JWT などの認証と、OpenTelemetry | README に、承認と Code Mode の記載が無い |
| Docker MCP Gateway (Go) | 複数のサーバーを束ね、profile ごとにツールを `<server>.<tool>` で指して有効・無効にする | README の OAuth は子への接続のためで、クライアントの利用者の認証の記載が無い。承認と OpenTelemetry の記載も無い |
| Cloudflare の `@cloudflare/codemode` | Code Mode の参照実装。Dynamic Worker (`WorkerLoader`) で動き、`globalOutbound: null` で外へ出さない | Workers の `worker_loaders` の binding が要る。自前のホストで動かす前提に合わない。README は Experimental と書く |
